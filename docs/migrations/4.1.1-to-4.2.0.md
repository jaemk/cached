# cached 4.1.1 to 4.2.0 migration

**Versions** `cached` 4.1.1 → 4.2.0, `cached_proc_macro` 3.0.1 → 3.1.0,
`cached_proc_macro_types` 3.0.0 → 3.1.0.

## Breaking changes

### Minimum supported Rust version is 1.95

- **Detection.** Check `rust-toolchain.toml`, CI images, and `rustc --version`.
- **Action.** Upgrade build and CI toolchains to Rust 1.95 or later before updating the
  dependency. All three crates in this release declare Rust 1.95.

### redb file locking

- **Detection.** Check whether processes on different cached versions open the same
  redb cache file.
- **Action.** Stop all processes using redb 4 before opening that file with cached 4.2.0
  and redb 5. The new release can read existing redb 4 cache files. Use separate cache
  files if both generations must run during the rollout.

## New APIs

- With `compression_zstd`, `RedisCacheBuilder`, `AsyncRedisCacheBuilder`, and
  `RedbCacheBuilder` accept `.compression(Compression::Zstd { level: 3 })`,
  `.min_compress_size(bytes)`, and `.max_decompressed_size(bytes)`. A build with the
  feature can read raw entries and zstd frames even when its builder writes raw entries.
- With `proc_macro`, `#[cached_skip]` excludes an argument from the cache key in
  `#[cached]` and `#[concurrent_cached]`. It still passes the argument to the function.
  Adopt it only when the omitted argument does not affect the cached result.

## Required Cargo.toml change

Keep your existing store and runtime features when updating the version.

```toml
# Before
cached = { version = "4.1.1", features = ["redis_store"] }

# After, with existing behavior
cached = { version = "4.2.0", features = ["redis_store"] }

# After, with zstd support for the rollout
cached = { version = "4.2.0", features = ["redis_store", "compression_zstd"] }
```

Use only one of these entries. Substitute your existing Redis runtime feature or `redb_store`
as applicable. Building with `compression_zstd` requires a C toolchain. If you pin a companion
crate directly, update its version to 3.1.0.

## Roll out compression on a shared cache

**Deploy zstd support to every reader before enabling compressed writes.** This includes
background workers and jobs that open the same Redis namespace or reuse the same redb file.

1. **Deploy readers first.** Build every reader with `compression_zstd` and leave
   `.compression(...)` unset on every writer. During this phase, new entries stay raw and
   older Redis clients can keep reading them.
2. **Verify the reader fleet.** Confirm all clients sharing the cache have zstd support.
   If a writer uses a custom `.max_decompressed_size(bytes)`, set every reader's limit
   at least as high as the largest writer limit. Include the serialized envelope in that
   size. A zstd-capable reader with a lower limit returns an error and preserves the frame.
3. **Enable writes.** Set `.compression(Compression::Zstd { level: 3 })` on the desired
   writers. Readers can consume both formats. Redb with refresh-on-hit rewrites the entry
   using its current compression settings, so treat those readers as writers too.

A client without zstd support cannot decode a compressed entry. In default self-healing
mode, a lookup can delete that entry and return a miss, causing repeated eviction and
recomputation during a mixed deployment. A strict lookup reports the error and preserves
the entry.

### Roll back compression

1. Disable compressed writes everywhere and keep every reader on a zstd-capable build.
2. Wait for existing compressed entries to expire, remove them from the affected cache,
   or switch clients to a fresh Redis namespace or redb file. With refresh-on-hit enabled,
   reads can extend Redis TTLs. Entries without a TTL need explicit removal or isolation.
3. Once older clients can no longer encounter a compressed entry, remove
   `compression_zstd` or roll back to a version without zstd support. If rolling redb back
   across the major dependency change, use a separate file or a pre-upgrade backup.

## VERIFY

```sh
rustc --version
cargo build
cargo test
```

For a compression rollout, use the same staging namespace or file to verify that a build
with zstd support reads existing raw values, then enable compressed writes on one writer
and verify that a second zstd-capable client with raw writes reads those values. In the
cached repository, `make tests/io-compression` exercises those cases across feature builds.

A missing `Compression` import or builder method means the build needs both
`compression_zstd` and a Redis or redb store feature.

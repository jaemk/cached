# cached 3.1 -> 4.0 Migration (Agent Instructions)

Versions: `cached 3.1.1` -> `cached 4.0.0`, `cached_proc_macro 3.0.0` -> `cached_proc_macro 3.0.1`.

`cached_proc_macro_types` did not change; leave it pinned at `3.0.0` if pinned directly.

MSRV is unchanged at 1.92.

## Breaking changes

### 1. Sharded lookups are generic over the key form, breaking `&&K` call sites

The six sharded stores (`ShardedUnboundCache`, `ShardedLruCache`, `ShardedTtlCache`,
`ShardedLruTtlCache`, `ShardedExpiringCache`, `ShardedExpiringLruCache`) changed their inherent
`get`, `remove`, `remove_entry`, `delete`, `contains`, and `peek` from `&K` to a generic borrowed
form:

```rust
// Before
pub fn get(&self, k: &K) -> Option<V>

// After
pub fn get<Q>(&self, k: &Q) -> Option<V>
where
    K: Borrow<Q>,
    Q: Hash + Eq + ?Sized,
    H: ShardHasher<Q>,
```

A call passing an extra reference used to compile through deref coercion and no longer does: `Q`
unifies to `&K` first, and the call fails with ``the trait bound `String: Borrow<&String>` is not
satisfied``. The same applies to `&Box<K>` and `&Arc<K>`.

Detection: search for a sharded-store lookup whose argument is already a reference. The loop form
is the common one:

```
rg 'for \w+ in &\w+' -A 3 | rg '\.(get|remove|remove_entry|delete|contains|peek)\(&'
rg '\.(get|remove|remove_entry|delete|contains|peek)\(&&'
```

Action: drop the extra `&`, or deref explicitly.

```rust
// Before
for k in &keys {
    cache.get(&k);
}
// After
for k in &keys {
    cache.get(k);
}

// Before
cache.get(&boxed_key);
// After
cache.get(&**boxed_key);
```

Single-owner stores are unaffected: `LruCache::cache_get` and friends were already generic over
`Q`, and `set` / `get_or_set_with` on the sharded stores are unchanged (they take the key by value
because they insert it).

### 2. `ShardHasher<K>` relaxed to `ShardHasher<K: ?Sized>`

```rust
// Before
pub trait ShardHasher<K>: Clone + Send + Sync + 'static
// After
pub trait ShardHasher<K: ?Sized>: Clone + Send + Sync + 'static
```

Detection: `rg 'ShardHasher<'` in your own generic code, not in impls.

Action: existing `impl ShardHasher<K> for MyRouter` blocks compile unchanged, since this only
widens what the trait accepts. A `H: ShardHasher<K>` bound no longer implies `K: Sized` at a use
site, so generic code that relied on that inference may need an explicit `K: Sized` bound.

### 3. Shard routing no longer consults `BuildHasher::hash_one`

The blanket `ShardHasher` impl for a `BuildHasher`, and every store's borrowed-key routing, now
build a `Hasher` with `build_hasher()`, hash the key, and finish it. `DefaultShardHasher`'s
`hash_one` override was removed, so it uses the provided default too.

Detection: `rg 'fn hash_one'` in your own `BuildHasher` impls.

Action: if you override `hash_one` on a hasher used to route a sharded store, move that logic into
the `Hasher` returned by `build_hasher()`. The upper-32-bit distribution contract for a custom
hasher now applies there. An override left in place is still used by `HashMap`, it is just no
longer consulted for shard routing.

This also changes shard assignment for keys under an affected hasher, so an entry inserted by 3.1
and a lookup under 4.0 can land on different shards. In-process caches are rebuilt on restart, so
this only matters if you persist a shard index across versions.

## New APIs

### `cached::claim::{ClaimRegistry, Claim}`

A single-flight claim on a key, for collapsing concurrent refreshes onto one caller. Ungated, no
new dependency. Reachable via `cached::claim::` or `cached::prelude`, not the crate root.

```rust
use cached::claim::ClaimRegistry;

let registry = ClaimRegistry::new();
if let Some(_claim) = registry.claim(key.clone()) {
    // only the first caller gets here; the key is released when `_claim` drops
}
```

`claim(key)` returns `Some(Claim<K>)` to the first caller and `None` to every later caller until
that `Claim` drops. Release happens in `Drop`, so completion, a panic, and an aborted async task
all release the key. The registry spawns nothing and awaits nothing; spawning the refresh stays
with the caller. `Debug for ClaimRegistry<K>` requires `K: Debug + Clone`.

See [design/0053](../../specs/design/0053-refresh-claim-guard.md).

### Capability traits

`CacheSetMaxSize` / `ConcurrentCacheSetMaxSize` reach `set_max_size` and `try_set_max_size` from a
generic bound; `CacheClearWithOnEvict` / `ConcurrentCacheClearWithOnEvict` reach
`cache_clear_with_on_evict` the same way. No new capability: both were already inherent methods
with the same eviction behavior.

Implemented by `LruCache`, `LruTtlCache`, `ExpiringLruCache`, `TtlSortedCache`, `ShardedLruCache`,
`ShardedLruTtlCache`, and `ShardedExpiringLruCache` for the max-size traits; by all 7 single-owner
and all 6 sharded in-memory stores for the clear-with-on-evict traits. Not implemented by the
unbounded stores (no live capacity to resize) or by `RedisCache` / `AsyncRedisCache` / `RedbCache`
(no client-side capacity, no `on_evict`).

All four are exported from `cached::prelude`.

### Borrowed keys on the sharded stores

The change in breaking item 1 is additive at every other call site: `sharded_cache.get("a")` now
works on a `ShardedLruCache<String, _>` without allocating a `String` first. The bound is on
`H: ShardHasher<Q>`, so a hand-written router keeps these six methods at every key type it
implements, not just where it also implements `BuildHasher`.

Contract, unenforced: every `ShardHasher` impl on one router must agree, `shard_hash(&k) ==
shard_hash(k.borrow())` for `K: Borrow<Q>`. A router with two disagreeing impls routes an owned
insert and its borrowed lookup to different shards, so `get` / `peek` / `contains` miss a present
entry and `remove` / `delete` silently no-op.

## Fixes worth knowing about

- `ShardedUnboundCache`, `ShardedTtlCache`, and `ShardedExpiringCache` route their intra-shard
  probe through `DefaultShardHasher` instead of the shard `HashMap`'s `BuildHasher::hash_one`, so
  an owned newtype key and its borrowed primitive form route to the same shard. The single-owner
  stores (`UnboundCache`, `TtlCache`, `ExpiringCache`, `TtlSortedCache`) are not covered; on a
  nightly compiler that enables ahash's `specialize` cfg, work around it with
  `.hasher(std::hash::RandomState::new())`.
- `TtlSortedCache::cache_clear_with_on_evict` counts an eviction per removed entry even with no
  `on_evict` configured. Observable if you meter evictions on that store.
- `#[cached]` and `#[once]` no longer trip clippy's `clone_on_copy` on rust 1.100+. If you
  suppressed this with `#[expect(clippy::clone_on_copy)]`, remove it: the expectation is now
  unfulfilled, which is itself an error under `-D warnings`. A plain `#[allow]` is harmless.

```toml
# Before
cached = "3.1.1"

# After
cached = "4.0.0"
```

```toml
# Before
cached_proc_macro = "3.0.0"

# After
cached_proc_macro = "3.0.1"
```

## VERIFY

```
cargo build
cargo test

```

Expected new compile errors:

- ``the trait bound `String: Borrow<&String>` is not satisfied`` (or `Box`/`Arc` in place of
  `String`) on a sharded `get` / `remove` / `remove_entry` / `delete` / `contains` / `peek`: drop
  the extra `&`, per breaking item 1.
- `error: this lint expectation is unfulfilled` under `-D warnings`: remove the
  `#[expect(clippy::clone_on_copy)]` on a `#[cached]` or `#[once]` function.

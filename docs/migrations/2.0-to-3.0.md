# cached 2.x → 3.0 Migration (Agent Instructions)

Versions: `cached 2.x` → `cached 3.0`. `cached_proc_macro` and `cached_proc_macro_types` both
bump to `3.0` in lockstep with `cached` (`cached_proc_macro_types` has a breaking change this
major: `Return<T>`'s fields went private, see #51).

## Required toolchain change

MSRV raised 1.85 → **1.92** (1.89 was required by `redb` 4.x; raised again to 1.92 for the
`async_core`/`async` feature, see #81). Update your toolchain if below 1.92.

## Breaking changes

### 1. `size` macro attribute removed

Detection: grep your code for `size = ` inside `#[cached(...)]` / `#[concurrent_cached(...)]`.

Action: rename to `max_size`.
```rust
// Before
#[cached(size = 100)]
// After
#[cached(max_size = 100)]
```

### 2. `ConcurrentCachedAsync` cache methods renamed (async_ prefix)

Detection: grep for calls to `.cache_get(` / `.cache_set(` / `.cache_remove(` / `.cache_remove_entry(` / `.cache_delete(` made through the `ConcurrentCachedAsync` trait (i.e. `.await`ed calls on a sharded/async store), or `ConcurrentCachedAsync::cache_*`.

Action: prefix with `async_`.
```rust
// Before
let v = store.cache_get(&k).await?;
store.cache_set(k, v).await?;
// After
let v = store.async_cache_get(&k).await?;
store.async_cache_set(k, v).await?;
```
The synchronous `ConcurrentCached` methods (`cache_get`/`cache_set`/…) are unchanged. This rename, together with the trait split below, lets you import both `ConcurrentCached` and `ConcurrentCachedAsync` without `E0034`.

If you have a custom `impl ConcurrentCachedAsync for YourStore`, rename the methods in the impl block too (`fn cache_get` → `fn async_cache_get`, etc.); otherwise the impl no longer matches the trait and fails to compile.

### 2b. Concurrent introspection/TTL/refresh-on-hit helpers moved to `ConcurrentCacheBase` / `ConcurrentCacheTtl` / `ConcurrentCacheRefreshOnHit`

`ConcurrentCached` and `ConcurrentCachedAsync` used to each declare the same synchronous helpers (`cache_size`, `ttl`, `set_ttl`, `unset_ttl`, `refresh_on_hit`, `set_refresh_on_hit`). On a store implementing *both* traits (`RedbCache`, every `Sharded*` store), calling one of those through method syntax with both traits in scope (as `cached::prelude::*` brings them) produced `error[E0034]: multiple applicable items in scope`.

Those helpers now live on three new shared traits:
- `ConcurrentCacheBase` — owns `type Error` and the introspection methods (`cache_size`, `cache_is_empty`). It is the supertrait of both `ConcurrentCached` and `ConcurrentCachedAsync` (mirroring how the single-owner `Cached` core is shared).
- `ConcurrentCacheTtl` — owns the global-TTL controls (`ttl`, `set_ttl`, `unset_ttl`) plus a new validated `try_set_ttl(Duration) -> Result<Option<Duration>, SetTtlError>` that rejects a zero `Duration` with `SetTtlError::ZeroTtl`. Only the TTL-capable concurrent stores implement it: `ShardedTtlCache`, `ShardedLruTtlCache`, `RedisCache`, `AsyncRedisCache`, `RedbCache`. Non-TTL sharded stores (`ShardedUnboundCache`, `ShardedLruCache`, `ShardedExpiringCache`, `ShardedExpiringLruCache`) no longer expose `set_ttl`/`ttl`/etc.
- `ConcurrentCacheRefreshOnHit` — owns `refresh_on_hit`/`set_refresh_on_hit`, split out of the TTL trait so satisfying the bound implies the capability (see #31). Implemented by the same TTL-capable stores except `RedbCache` is included and `TtlSortedCache` has no concurrent counterpart to worry about; concretely: `ShardedTtlCache`, `ShardedLruTtlCache`, `RedisCache`, `AsyncRedisCache`, `RedbCache`.

All three new traits are re-exported from the crate root and from `cached::prelude`.

Action:
- Callers using `cached::prelude::*`: no change — all three new traits come in with the glob.
- Callers importing the concurrent traits individually (e.g. `use cached::ConcurrentCached;`) and calling `cache_size`/`cache_is_empty`, `set_ttl`/`ttl`/`unset_ttl`, or `refresh_on_hit`/`set_refresh_on_hit`: add `ConcurrentCacheBase`, `ConcurrentCacheTtl`, and/or `ConcurrentCacheRefreshOnHit` to the import as needed. Note: the introspection method on the trait is `cache_size`/`cache_is_empty`. The shorter `len`/`is_empty` names are available on the `ConcurrentCachedExt` alias trait (new in 3.0; the concurrent traits had neither name in 2.0.2), returning `Result<Option<usize>, Self::Error>` / `Result<Option<bool>, Self::Error>` rather than plain values. The inherent `len()`/`is_empty()` on the six sharded concrete types return plain values and take call-site priority over the aliases.
- Custom `impl ConcurrentCached`/`ConcurrentCachedAsync` for your own store: move the `type Error` (and any `cache_size`/`cache_is_empty` override) into a single `impl ConcurrentCacheBase for YourStore` block, TTL behavior into `impl ConcurrentCacheTtl for YourStore`, and refresh-on-hit behavior into a separate `impl ConcurrentCacheRefreshOnHit for YourStore`:
  ```rust
  use cached::{ConcurrentCacheBase, ConcurrentCached};

  impl ConcurrentCacheBase for MyStore {
      type Error = std::convert::Infallible;
  }
  impl ConcurrentCached<String, u32> for MyStore {
      // cache_get / cache_set / cache_remove / cache_remove_entry / cache_clear / cache_reset ...
  }
  ```

### 3. `CacheTtl` / `CacheEvict` removed from concurrent stores

`CacheTtl` and `CacheEvict` are now single-owner (`&mut self`) traits, no longer implemented for `RedbCache` (the renamed `DiskCache`, see #6), `RedisCache`, `AsyncRedisCache`, or the sharded stores.

Detection: grep for `CacheTtl::set_ttl`/`set_ttl(&mut` and `CacheEvict::evict`/`evict(&mut` on a sharded/disk/redis store.

Action:
- TTL on a concurrent store: use the `&self` methods from `ConcurrentCacheTtl`:
  ```rust
  use cached::ConcurrentCacheTtl;
  // Before
  CacheTtl::set_ttl(&mut store, Duration::from_secs(30));
  // After
  ConcurrentCacheTtl::set_ttl(&store, Duration::from_secs(30)); // works through Arc/static
  ```
- Eviction on a sharded store: use the new `ConcurrentCacheEvict` trait or the inherent `evict(&self)`:
  ```rust
  use cached::ConcurrentCacheEvict;
  let n = store.evict(); // &self
  ```
  `ConcurrentCacheEvict` is implemented only by the four TTL/expiring sharded stores (`ShardedTtlCache`, `ShardedLruTtlCache`, `ShardedExpiringCache`, `ShardedExpiringLruCache`). `ShardedUnboundCache` and `ShardedLruCache` have no expiry and never implemented `CacheEvict`, so they gain nothing here.
Single-owner in-memory stores keep `CacheTtl`/`CacheEvict` unchanged: `CacheTtl` on `TtlCache`, `LruTtlCache`, `TtlSortedCache`; `CacheEvict` on all five (`TtlCache`, `LruTtlCache`, `TtlSortedCache`, `ExpiringCache`, `ExpiringLruCache`). `ExpiringCache`/`ExpiringLruCache` use per-value expiry and never implemented `CacheTtl`.

### 4. `CacheMetrics.size` renamed to `entry_count`, now `Option<usize>`

Detection: grep for `.size` on a `CacheMetrics` value, or `CacheMetrics { ... size: ... }`; a
type error binding `.entry_count` as a `usize` surfaces the type change.

Action: rename the field access/initializer to `entry_count`. The field type also changed from
`usize` to `Option<usize>`: stores that cannot report a count (`RedisCache` / `RedbCache`) now
yield `None` from `metrics()` instead of a misleading `0`. Match on the `Option` (or use
`.unwrap_or(0)` to keep the old scalar).

`CacheMetrics` is also now `#[non_exhaustive]` and derives `Default`. A struct-literal
construction outside the crate (`CacheMetrics { hits, misses, entry_count }`) no longer compiles
and an exhaustive `{ .. }` field match must add a `..` rest pattern; build one with
`CacheMetrics::default()` and set the fields you need, and read it through the field accessors.

### 5. Builder `refresh()` → `refresh_on_hit()`

Detection: grep for `.refresh(` on a cache builder (`TtlCacheBuilder`, `LruTtlCacheBuilder`, sharded TTL builders, the 2.x `DiskCacheBuilder` — renamed `RedbCacheBuilder` in 3.0, see #6 — `RedisCacheBuilder`, `AsyncRedisCacheBuilder`).

Action: rename the builder method call to `.refresh_on_hit(`. The `#[cached(refresh = true)]` macro attribute is unchanged.

### 6. `DiskCache` backend changed from sled to redb

- Rename: the canonical type is now `RedbCache` (it names its backend explicitly, like `RedisCache`). The old `DiskCache` / `DiskCacheBuilder` / `DiskCacheError` / `DiskCacheBuildError` names are removed, not kept as aliases (see #23): rename every use to the `Redb*` equivalent.
- On-disk format changed: existing on-disk caches are not read (entries are recomputed). No code change needed for the common case. The previous sled cache directories (named `<cache_name>_v1/`) are neither read nor removed, so they linger as dead files under the system cache directory (`$system_cache_dir/<exe>_cached_disk_cache/`), or under whatever path you passed to the 2.x `disk_directory(...)` builder method (renamed to `disk_dir`, see #69) / `disk_dir = "..."`; delete them manually to reclaim the space.
- Detection: grep for `sled`, `DiskCache::connection`, `connection_mut`, `connection_config`, and matches on `DiskCacheError`/`DiskCacheBuildError`.
- Action:
  - Remove any use of `DiskCacheBuilder::connection_config(...)` and the `connection_config = "..."` `#[concurrent_cached]` attribute (removed).
  - Remove any use of `DiskCache::connection()` / `connection_mut()` (removed; the redb handle is not exposed).
  - `RedbCacheError::Storage` / `RedbCacheBuildError::Storage` now wrap `redb::Error` (both are struct variants with a `source` field, see #7); `RedbCacheBuildError` has a new `Io` variant and no longer has the (never-constructed) `MissingDiskPath` variant. Update exhaustive matches.
  - `durable` defaults to `true` (durable, fsync per write). Set `false` to trade durability for write throughput: writes then use `Durability::None` and are not persisted until a later durable commit (so they can be lost on process exit or crash); call `RedbCache::flush()` / `async_flush()` to force one. Note that this is a change in default: the sled-backed store defaulted to non-durable (no fsync per write). If you relied on that fast default, set `durable(false)` (or the `durable = false` macro attribute) to keep the old write-throughput behavior.
  - The builder method and `#[concurrent_cached]` attribute `sync_to_disk_on_cache_change` were renamed to `durable` (detection: grep for `sync_to_disk_on_cache_change`; action: rename to `durable`).
- Concurrency: redb is single-writer, so write operations on one `RedbCache` are serialized (reads stay concurrent via MVCC), whereas sled allowed concurrent writers. This is fine for read-heavy caching; for write-heavy concurrent use, spread load across multiple `RedbCache` instances, each with a distinct cache name (redb holds an exclusive lock on its file, so two instances cannot share one name/path). No code change required. Through the `#[concurrent_cached(disk = true)]` macro the store builder panics on build failure, so failing to acquire that exclusive file lock (for example a second concurrent process of the same binary sharing the default path) surfaces as a panic at the first cache call rather than through your function's `Result`. Give each process a distinct `disk_dir` / cache name if they must run concurrently.
- Cache name validation: `cache_name` is used as a filename component and is now validated to reject characters invalid in a filename: path separators (`/` or `\`), path-traversal components (`.` or `..`), the filename-reserved characters `:` `<` `>` `"` `|` `?` `*`, and ASCII control characters (see #55). A `:`-bearing name, including one derived from `module_path!()`, is no longer accepted (it was invalid on Windows/NTFS). If you set a dynamic `cache_name` (e.g. via `.name(...)` on the builder or the `name = "..."` macro attribute), sanitize it to the allowed set first; a `module_path!()`-derived name needs its `::` separators replaced (for example with `_`). Detection: a `RedbCacheBuildError::InvalidCacheName` at cache construction time if the name contains a forbidden component.
- `RedbCache::remove_expired_entries` now returns `Result<usize, _>` (the number of entries swept) instead of `Result<(), _>`. Detection: a type mismatch on the old `()` return. Action: bind or ignore the count (`let _ = cache.remove_expired_entries()?;`).

### 7. Store error enums: variants renamed and `#[non_exhaustive]`

The public store error enums dropped the redundant `Error` suffix from their variant names, and are now `#[non_exhaustive]`.

Detection: grep for matches on `RedbCacheError`, `RedbCacheBuildError`, `RedisCacheError`, `RedisCacheBuildError` (or, from 2.x, the removed `DiskCacheError` / `DiskCacheBuildError` names).

Action:
- Rename matched variants:
  - `RedbCacheError`: `StorageError` → `Storage`, `CacheDeserializationError` → `CacheDeserialization`, `CacheSerializationError` → `CacheSerialization` (`BackgroundTaskFailed` removed, see #38).
  - `RedbCacheBuildError`: `ConnectionError` → `Storage` (the variant names the backend, matching `RedbCacheError::Storage`; redb has no connection).
  - `RedisCacheError`: `RedisCacheError` → `Redis`, `PoolError` → `Pool`, `CacheDeserializationError` → `CacheDeserialization`, `CacheSerializationError` → `CacheSerialization`.
  - `RedisCacheBuildError` was already suffix-free; no change.
- The `RedbCacheError` and `RedbCacheBuildError` variants are now struct variants (named fields) matching the redis enums, so tuple patterns like `CacheSerialization(e)` become `CacheSerialization { source }`. Every foreign cause is boxed: `source` is `Box<dyn std::error::Error + Send + Sync + 'static>` on all four backend error enums, not a concrete backend type. Only the deserialize variants carry `cached_value: Vec<u8>` (the raw bytes that failed to decode): `RedbCacheError::CacheDeserialization` and `RedisCacheError::CacheDeserialization` are `{ source, cached_value }`, while the `CacheSerialization` variants are `{ source }` only. Binding `source` as a concrete `rmp_serde::encode::Error` / `rmp_serde::decode::Error` / `serde_json::Error` no longer compiles; see #59 for how to inspect a cause.
- These enums (plus `cached::stores::BuildError`) are now `#[non_exhaustive]`, so an exhaustive `match` must add a wildcard arm (`_ => ...`). `TtlSortedCache` has no error type to mark: its `Error` is `std::convert::Infallible` in 3.0 (see #18 and #43).

### 8. Redis TLS features split

`redis_tokio` and `redis_smol` no longer imply native-tls; they now enable the TLS-agnostic
`redis/tokio-comp` / `redis/smol-comp` connection paths.

Detection: a `rediss://` (TLS) Redis URL that previously connected now fails, or a build/link
error about a missing TLS connector. This includes users who relied solely on `redis_async_cache`
(which previously implied `native-tls` and no longer does).

Action: add a TLS backend feature alongside the runtime feature:
- Tokio + system TLS: `redis_tokio_native_tls`; Tokio + rustls: `redis_tokio_rustls`.
- smol + system TLS: `redis_smol_native_tls`; smol + rustls: `redis_smol_rustls`.

`redis_async_cache` is now TLS- and runtime-agnostic: `redis_async_cache = ["redis_store",
"async", "redis/cache-aio"]`, with no runtime of its own. Pair it with a `redis_tokio*` or
`redis_smol*` runtime feature (add the `_native_tls` / `_rustls` variant if TLS is required).
`redis_connection_manager` is likewise additive and runtime-agnostic, and gates a per-cache
`.connection_manager(true)` opt-in rather than cfg-swapping every cache's connection type as in
2.x. See #57 for the full capability/runtime feature axis.

### 9. `RedisCacheBuilder::build()` / `AsyncRedisCacheBuilder::build()` reject an empty prefix

The prefix is what distinguishes logical caches sharing a namespace: two that both leave it
empty share one keyspace and one `cache_clear` / `async_cache_clear` scope (`<namespace>::*`, or
`cached-redis-store::*` under the shared default namespace), so each reads, overwrites and
deletes the other's entries. In 2.x an empty prefix was accepted silently; `build()` now returns
`Err(RedisCacheBuildError::Build(BuildError::InvalidValue { field: "prefix", .. }))` for a
prefix explicitly set to `""` (an unset prefix still returns
`Build(BuildError::MissingRequired("prefix"))`).

Detection: a `build()` call returns the `InvalidValue { field: "prefix", .. }` error at runtime,
or (on the `redis = true` macro path, where the builder is called internally) a panic at the
first cache call. Grep for `.prefix("")` and `RedisCache::builder("")` /
`AsyncRedisCache::builder("")`.

Action: give each logical cache a distinct non-empty prefix. The
`#[concurrent_cached(redis = true)]` macro always supplies the function name as the cache
prefix, so macro-generated caches are unaffected. If you previously used an empty prefix with a
custom namespace as the scope, move that scope string into the prefix (e.g.
`.prefix("my-scope")`); key layout stays `{namespace}:{prefix}:{key}`.

Note for 3.0 release-candidate users: the `RedisCacheBuildError::EmptyScope` variant, which
fired only when namespace and prefix were both empty, does not exist in 3.0.0; the
empty-prefix rejection above subsumes it.

### 10. `get_or_set_with` family returns `&V` instead of `&mut V`

`Cached::cache_get_or_set_with` / `cache_try_get_or_set_with` (and their `get_or_set_with` /
`try_get_or_set_with` aliases) and `CachedGetOrSetAsync::async_cache_get_or_set_with` /
`async_cache_try_get_or_set_with` now return `&V` / `Result<&V, E>` (previously `&mut V` /
`Result<&mut V, E>`).

Detection: a compile error mutating the returned reference, or a type mismatch binding it as `&mut V`. A custom `impl Cached` will fail with a missing-required-method error for `cache_get_or_set_with_mut` and `cache_try_get_or_set_with_mut` (not a mutation error on the call site). `CachedGetOrSetAsync::async_cache_get_or_set_with` now returns `&V` / `Result<&V, E>`; the new `async_cache_get_or_set_with_mut` preserves the `&mut V` / `Result<&mut V, E>` behavior.

Action: if you only read the value, most call sites need no change (a `&mut V` reborrows to `&V`
implicitly). The exception is a binding that explicitly names the old type (e.g.
`let v: &mut V = cache.get_or_set_with(...)`) or a pattern expecting `&mut V`: drop the `mut` from
the annotation. To actually mutate, switch to the new `*_mut` variants (`cache_get_or_set_with_mut`,
`cache_try_get_or_set_with_mut`, `get_or_set_with_mut`, `try_get_or_set_with_mut`,
`async_cache_get_or_set_with_mut`, `async_cache_try_get_or_set_with_mut`). Custom `impl`s of `Cached` /
`CachedGetOrSetAsync` must update the method signatures and implement the new required methods:
`cache_get_or_set_with_mut` and `cache_try_get_or_set_with_mut` (and, for `CachedGetOrSetAsync`,
`async_cache_get_or_set_with_mut` and `async_cache_try_get_or_set_with_mut`). The `get_or_set_with_mut` /
`try_get_or_set_with_mut` aliases and the non-`mut` `&V` methods are provided as defaults.

### 11. `new()` added to in-memory stores; `new()` removed from I/O stores

**In-memory stores** (`UnboundCache`, `LruCache`, `TtlCache`, `LruTtlCache`, `TtlSortedCache`,
`ExpiringCache`, `ExpiringLruCache`, and the six sharded variants) now have a `new()` (or
`new(required_field)`) constructor that returns a ready-to-use cache. This is additive: `builder()`
still exists and is preferred when you need non-default configuration.

```rust
// Now valid — previously these stores had no ::new()
let cache: UnboundCache<String, u32> = UnboundCache::new();
let cache: LruCache<String, u32> = LruCache::new(100);           // max_size required
let cache: TtlCache<String, u32> = TtlCache::new(Duration::from_secs(60)); // ttl required
let cache: LruTtlCache<String, u32> = LruTtlCache::new(100, Duration::from_secs(60));
```

**I/O stores** (`RedbCache`, `RedisCache`, `AsyncRedisCache`) previously had a `new(...)` that
returned a *builder*, which conflicted with the convention that `new()` returns a ready store.
That `new()` is now removed. Use `builder(...)` directly.

`builder(...)` itself also changed this major (see #26): the primary required field is now positional. The final form is:
```rust
// Before
let builder = RedbCache::<String, String>::new("my-cache");
// After
let builder = RedbCache::<String, String>::builder("my-cache");

// Before
let builder = RedisCache::<String, String>::new("prefix", ttl);
// After
let builder = RedisCache::<String, String>::builder("prefix").ttl(ttl);

// Before
let builder = AsyncRedisCache::<String, String>::new("prefix", ttl);
// After
let builder = AsyncRedisCache::<String, String>::builder("prefix").ttl(ttl);
```

Detection: grep for `RedbCache::new(`, `RedisCache::new(`, `AsyncRedisCache::new(`.

Action: replace `::new(` with `::builder(primary_arg)` on the cache types `RedbCache` /
`RedisCache` / `AsyncRedisCache` only, passing the primary required field positionally as shown
above (see #26 for details). Any additional options (`.ttl(...)`, `.durable(...)`, etc.) chain
as builder setters. The `*Builder::new` constructors (`RedbCacheBuilder::new`,
`RedisCacheBuilder::new`, `AsyncRedisCacheBuilder::new`) still exist and are unchanged, so scope
the change to the three cache types and do not rewrite those.

### 12. Macro `ttl` attribute changed: `ttl_secs`, `ttl_millis`, or Duration expression

The `#[cached]` / `#[once]` / `#[concurrent_cached]` macro attribute `ttl = <integer>` (whole
seconds as a bare integer) is removed. Three mutually exclusive forms replace it:

| Attribute | Meaning |
|---|---|
| `ttl_secs = N` | N whole seconds (replaces the old `ttl = N` integer form) |
| `ttl_millis = N` | N milliseconds (new in this release) |
| `ttl = "Duration::from_secs(N)"` | arbitrary Duration expression (string literal) |

Using more than one of these on the same annotation, or combining any of them with `expires`, is
a compile error. `ttl_secs` and `ttl_millis` must be >= 1.

Using the old `ttl = <integer>` form now produces an error like:
"`ttl` now takes a Duration expression (e.g. `ttl = \"Duration::from_secs(60)\"`); for whole
seconds use `ttl_secs = 60`, for milliseconds use `ttl_millis = 500`."

**Detection:** grep for `ttl = ` inside `#[cached(...)]` / `#[once(...)]` / `#[concurrent_cached(...)]`
where the value is a bare integer.

**Action — `#[cached]`:**
```rust
// Before
#[cached(ttl = 60)]
fn fetch_data(id: u32) -> String { ... }

// After: option A - whole seconds (preferred)
#[cached(ttl_secs = 60)]
fn fetch_data(id: u32) -> String { ... }

// After: option B - Duration expression
#[cached(ttl = "cached::time::Duration::from_secs(60)")]
fn fetch_data(id: u32) -> String { ... }
```
Note: option B inlines the expression verbatim, so `Duration` must be in scope at the
call site (use the fully-qualified path above, or add `use cached::time::Duration;`).
Option A (`ttl_secs`) needs no import.

**Action — `#[once]`:**
```rust
// Before
#[once(ttl = 30)]
fn config() -> Config { ... }

// After
#[once(ttl_secs = 30)]
fn config() -> Config { ... }
```

**Action — `#[concurrent_cached]`:**
```rust
// Before
#[concurrent_cached(ttl = 120)]
async fn fetch(id: u32) -> Result<String, Error> { ... }

// Before (combined with max_size)
#[concurrent_cached(max_size = 500, ttl = 120)]
async fn fetch(id: u32) -> Result<String, Error> { ... }

// After
#[concurrent_cached(ttl_secs = 120)]
async fn fetch(id: u32) -> Result<String, Error> { ... }

#[concurrent_cached(max_size = 500, ttl_secs = 120)]
async fn fetch(id: u32) -> Result<String, Error> { ... }
```

**Builder `.ttl(Duration)` is unchanged.** The Rust method `.ttl(Duration::from_secs(60))` on a
builder still works. Additionally, builders now have convenience methods `.ttl_secs(n)` and
`.ttl_millis(n)` that map to `Duration::from_secs(n)` / `Duration::from_millis(n)`. All three
builder methods target the same underlying field; whichever is called last wins.

```rust
// All equivalent at the builder level:
TtlCache::builder()
    .ttl(Duration::from_secs(60))
    .build()?;

TtlCache::builder()
    .ttl_secs(60)
    .build()?;

TtlCache::builder()
    .ttl_millis(500)
    .build()?;
```

Note: the builder-level `.ttl_secs` / `.ttl_millis` methods do not enforce mutual exclusion at
compile time (last call wins). The three-way mutual exclusion is a macro attribute constraint only.

### 13. Short method aliases moved to `CachedExt` / `ConcurrentCachedExt`

The `Cached` and `ConcurrentCached` traits keep only the `cache_`-prefixed methods (`cache_get`,
`cache_set`, `cache_remove`, `cache_clear`, `cache_size`, ...). The short aliases (`get`, `set`,
`remove`, `clear`, `len`, `is_empty`, `delete`, `try_set`, `contains`, `hits`, `misses`,
`metrics`, and the short `get_or_set_with` family) now live on blanket extension traits
`CachedExt` / `ConcurrentCachedExt`, implemented for every `Cached` / `ConcurrentCached` type.
This shrinks the surface a custom store must implement (only the `cache_`-prefixed methods) while
keeping every caller-facing name.

Detection: `no method named get`/`set`/`len`/... found on a cache value, where the short alias
previously resolved through `Cached` / `ConcurrentCached`.

Action: bring the extension trait into scope. `use cached::prelude::*;` imports both the core and
extension traits. Otherwise add `use cached::CachedExt;` (or `use cached::ConcurrentCachedExt;`)
alongside the core trait, or call the `cache_`-prefixed method on the core trait directly. A
custom `impl Cached` / `impl ConcurrentCached` no longer implements the short aliases (they are
provided by the blanket impl); remove any short-alias methods from such impls.

### 14. Sharded `*Base` types collapsed into one defaulted-hasher type; `*Base` no longer exists

Each sharded store used to ship three public names: `ShardedXBase<K, V, H>` (the fully generic
struct every trait actually implemented on), the two-parameter alias
`ShardedX<K, V> = ShardedXBase<K, V, DefaultShardHasher>` that most code wrote, and
`ShardedXBuilder<K, V, H>`. `H` lived only on `*Base`, so `*Base` was the name rustc printed in
every diagnostic and every rustdoc impl block even though user code wrote `ShardedX`:

```text
error[E0599]: no method named `set_ttl` found for struct `ShardedUnboundCacheBase<K, V, H>`
```

3.0 collapses the struct and its alias into a single generic type with a defaulted third
parameter, mirroring `std::collections::HashMap<K, V, S = RandomState>`:

```rust
pub struct ShardedUnboundCache<K, V, H = DefaultShardHasher> { .. }
```

Applied to all six: `ShardedUnboundCache`, `ShardedLruCache`, `ShardedTtlCache`,
`ShardedLruTtlCache`, `ShardedExpiringCache`, `ShardedExpiringLruCache`. **There is no deprecated
alias** — `ShardedUnboundCacheBase`, `ShardedLruCacheBase`, `ShardedTtlCacheBase`,
`ShardedLruTtlCacheBase`, `ShardedExpiringCacheBase`, and `ShardedExpiringLruCacheBase` do not
exist anywhere in the crate (crate root, `cached::stores`, `cached::stores::sharded`) as of 3.0.
Builder types are untouched: `ShardedXBuilder<K, V, H>` already carried `H` and keeps its name.

Detection: grep for any `*Base` spelling of a sharded store name in `use` statements, type
annotations, turbofish, or trait impls: `ShardedUnboundCacheBase`, `ShardedLruCacheBase`,
`ShardedTtlCacheBase`, `ShardedLruTtlCacheBase`, `ShardedExpiringCacheBase`,
`ShardedExpiringLruCacheBase`. Each now fails with `cannot find type ... in this scope` (or, if it
resolved to something else entirely, an unrelated type error).

Action: mechanical rename, drop `Base` from the name. If a custom hasher was named through the
turbofish, it now goes on the same type (the third parameter is defaulted, not a separate struct):

```rust
// Before (2.0.2)
let cache = ShardedLruCacheBase::<u32, u32, MyHasher>::builder()
    .hasher(MyHasher::default())
    .max_size(1000)
    .build()
    .unwrap();
let typed: ShardedLruCacheBase<u32, u32, MyHasher> = cache;

// After (3.0): drop `Base`. The turbofish names only K and V -- `builder()` lives on the
// default-hasher inherent impl block, so naming the hasher there does not compile (see
// below). The custom hasher is introduced by `.hasher(..)`, which switches the builder's H.
let cache = ShardedLruCache::<u32, u32>::builder()
    .hasher(MyHasher::default())
    .max_size(1000)
    .build()
    .unwrap();
let typed: ShardedLruCache<u32, u32, MyHasher> = cache;
```

A custom hasher is introduced only through `ShardedX::builder().hasher(h)`, which switches the
builder's `H` and whose `build` yields `ShardedX<K, V, H>`; `new()` and `builder()` stay on the
default-hasher inherent impl block (`impl<K, V> ShardedX<K, V, DefaultShardHasher>`), so
`ShardedX::<_, _, CustomHasher>::new()` / `::builder()` still fail to compile rather than silently
falling back to `DefaultShardHasher`.

Diagnostics and rustdoc now name `ShardedX` directly, so no downstream call site needs to know the
`*Base` name ever existed.

### 15. `cache_clear` / `cache_reset` are now required on the concurrent traits

Only affects custom `impl ConcurrentCached` / `impl ConcurrentCachedAsync` for your own store. Their previous no-op `Ok(())` defaults silently did nothing; every built-in store already overrides them.

Detection: a `.refresh_on_hit()` / `.set_refresh_on_hit()` call on a `TtlCache` / `LruTtlCache` value (not the builder) that fails to resolve, or that previously discarded the setter's `()` return.

Action: bring `CacheRefreshOnHit` into scope; the trait setter returns the previous `bool`.
```rust

```
The builder method `TtlCacheBuilder::refresh_on_hit(self, bool) -> Self` is unchanged.

### 27. `CachedAsync` renamed to `CachedGetOrSetAsync`; async passthroughs removed; get-or-set methods renamed (I1)

The in-memory async-closure trait `CachedAsync` is renamed to `CachedGetOrSetAsync`. It only memoizes an async closure over a synchronous in-memory `Cached` store; it is not a general async cache surface (that is `ConcurrentCachedAsync`, unchanged here). Three things changed:

- The trait and its import are renamed: `cached::CachedAsync` -> `cached::CachedGetOrSetAsync` (the prelude re-exports the new name).
- The four sync passthrough methods `async_cache_get` / `async_cache_set` / `async_cache_remove` / `async_cache_clear` are removed. They only forwarded to the synchronous `Cached` methods; call those directly (no `.await`).
- The get-or-set methods keep the `async_cache_*` namespace (renamed in this major from the 2.x `async_get_or_set_with*` spellings).

Detection: unresolved import `cached::CachedAsync`; `no method named async_cache_get` (and `_set` / `_remove` / `_clear`) on an in-memory store; and, from 2.x, `grep -rn 'async_get_or_set_with\|async_try_get_or_set_with\|get_async\|set_async\|remove_async\|clear_async'` (exclude hits that already start with `async_cache_`).

Action: rename the import, replace the removed passthroughs with the sync `Cached` methods, and add `cache_` after the `async_` prefix on the get-or-set calls.
```rust
// Import
// Before
use cached::CachedAsync;
// After
use cached::CachedGetOrSetAsync;

// Removed passthroughs: call the sync `Cached` methods directly (no await)
// Before
let v = cache.async_cache_get(&key).await;
cache.async_cache_set(key, value).await;
cache.async_cache_remove(&key).await;
cache.async_cache_clear().await;
// After
let v = cache.cache_get(&key);
cache.cache_set(key, value);
cache.cache_remove(&key);
cache.cache_clear();

// Get-or-set family (the async-closure memoization this trait exists for)
// Before (2.x)
cache.async_get_or_set_with(key, || async { value }).await
// After
cache.async_cache_get_or_set_with(key, || async { value }).await
// Same shape for `async_cache_get_or_set_with_mut`, `async_cache_try_get_or_set_with`, and `_try_..._mut`.
```

Custom `impl CachedGetOrSetAsync` blocks implement only the get-or-set `_mut` methods; drop any passthrough overrides and rename the trait in the `impl` header.

### 29. `set_ttl(Duration::ZERO)` disables expiry for future inserts only (I2)

A zero `Duration` passed to `set_ttl` now means "expiry disabled" -- exactly equivalent to `unset_ttl()`, with future-inserted entries never expiring. This is uniform across every `set_ttl` surface: the sharded `ShardedTtlCache` / `ShardedLruTtlCache`, the single-owner `TtlCache` / `LruTtlCache` / `TtlSortedCache`, and `RedisCache` / `AsyncRedisCache`.

- Previously the sharded stores **panicked** on `Duration::ZERO`; they no longer do.
- Previously a zero TTL meant "expire immediately" on the single-owner and Redis stores; it now means "never expire".
- For the Redis stores, a disabled TTL writes keys **without any expiry** (a plain `SET` instead of `SETEX`), and the refresh-on-hit path issues no `EXPIRE`. Re-arm expiry with `set_ttl(nonzero)`.
- `build()` still rejects a zero TTL (`BuildError::InvalidValue` / `MissingRequired`), and `CacheTtl::try_set_ttl(0)` still returns `Err(SetTtlError::ZeroTtl)` -- these are the strict "give me a real ttl" paths.
- `TtlSortedCache` now matches the other TTL stores on every axis. A zero TTL disables expiry for future inserts (previously it meant immediate expiry); its per-entry expiry is now `Option<Instant>` (`None` = never expires), ordered so never-expiring entries are evicted last under a size cap. The `CacheTtl` getter is aligned too: `ttl()` / `set_ttl` / `unset_ttl` resolve a zero TTL to `None` (previously `ttl()` returned `Some(Duration::ZERO)`), matching `TtlCache` / `LruTtlCache`. And a `cache_set` whose expiry would overflow `Instant` bounds now stores a never-expiring entry instead of silently dropping the value, again matching `TtlCache` / `LruTtlCache`.
- Because TTL stores now track per-entry expiry (#32 below), `set_ttl` applies to future inserts only. Entries already in the store keep their computed expiry; `set_ttl(0)` / `unset_ttl()` does not retroactively strip expiry from existing entries.

Detection: `grep -rn 'set_ttl'` for call sites that pass a `Duration` that could be zero and relied on either the panic (sharded) or the immediate-expiry behavior (single-owner / Redis).

Action: if you relied on a zero TTL expiring entries immediately, that behavior is gone -- pass a small non-zero `Duration` instead. If you want a zero TTL rejected as a caller error, use `CacheTtl::try_set_ttl`, which returns `Err(SetTtlError::ZeroTtl)`. To disable expiry, call `set_ttl(0)` or `unset_ttl()`. No change is required for call sites that already pass a non-zero duration.

### 30. `#[cached(refresh = true)]` requires a TTL (I7)

Using `refresh = true` on `#[cached]` without a TTL (`ttl_secs`, `ttl_millis`, or `ttl`) is now a compile error. Previously it was silently ignored.

Detection: `grep -rn 'refresh\s*=\s*true'` inside `#[cached(...)]` annotations; then check whether a TTL attribute is also present.

Action: add a TTL attribute alongside `refresh = true`, or remove `refresh = true` if it was unintentional.
```rust

// After: either add a TTL

```

### 31. `refresh_on_hit` / `set_refresh_on_hit` split off `CacheTtl` / `ConcurrentCacheTtl` into new `CacheRefreshOnHit` / `ConcurrentCacheRefreshOnHit` traits

In 2.0.2, `CacheTtl` carried five methods: `ttl`, `set_ttl`, `unset_ttl`, `refresh_on_hit`,
`set_refresh_on_hit`. There was no `ConcurrentCacheTtl` trait; the concurrent equivalents lived
directly on `ConcurrentCached`/`ConcurrentCachedAsync`, which had `ttl`/`set_ttl`/`unset_ttl` and a
`set_refresh_on_hit` setter but no `refresh_on_hit` getter. In 3.0 the two TTL traits keep only
`ttl`/`set_ttl`/`try_set_ttl`/`unset_ttl` (`try_set_ttl` is new in 3.0; see the New APIs list).
`refresh_on_hit`/`set_refresh_on_hit` moved to two
new required-method traits: `CacheRefreshOnHit` (`&self` getter, `&mut self` setter) implemented
by `TtlCache` and `LruTtlCache`; `ConcurrentCacheRefreshOnHit` (`&self` on both) implemented by
`ShardedTtlCache`, `ShardedLruTtlCache`, `RedisCache`, `AsyncRedisCache`, `RedbCache`. Both are
re-exported from the crate root and `cached::prelude`.

`TtlSortedCache` does **not** implement `CacheRefreshOnHit`. Its 2.0.2 `refresh_on_hit`/
`set_refresh_on_hit` were a no-op that discarded the setter's argument and always returned
`false` (`TtlSortedCache` keeps entries in a deadline-ordered index that a refreshed expiry would
leave unsorted, so it genuinely cannot support the feature). In 3.0 `TtlSortedCache` has neither
method at all; generic code bounded on `CacheRefreshOnHit` no longer accepts it, instead of
silently doing nothing at runtime.

Detection:
- A custom `impl CacheTtl for X` or `impl ConcurrentCacheTtl for X` that still defines
  `refresh_on_hit`/`set_refresh_on_hit` now gets an "unknown associated item" / unused-`impl`
  warning-turned-error, since those names are no longer part of the trait.
- A `.refresh_on_hit()` / `.set_refresh_on_hit()` call reached through `CacheTtl::` or
  `ConcurrentCacheTtl::` UFCS syntax fails to resolve.
- A `.refresh_on_hit()` / `.set_refresh_on_hit()` call on a `TtlSortedCache` value now fails to
  compile (previously a silent no-op).

Action: move the two methods into a separate `impl CacheRefreshOnHit for X` /
`impl ConcurrentCacheRefreshOnHit for X` block, and switch fully-qualified call sites to the new
trait name:
```rust
// CacheRefreshOnHit (single-owner stores: TtlCache, LruTtlCache)
impl CacheRefreshOnHit for MyStore {
    fn refresh_on_hit(&self) -> bool { self.refresh }
    fn set_refresh_on_hit(&mut self, refresh: bool) -> bool {
        std::mem::replace(&mut self.refresh, refresh)
    }
}

// ConcurrentCacheRefreshOnHit (concurrent stores: sharded TTL, RedisCache, RedbCache)
impl ConcurrentCacheRefreshOnHit for MyStore {
    fn refresh_on_hit(&self) -> bool { self.refresh.load(Ordering::Relaxed) }
    fn set_refresh_on_hit(&self, refresh: bool) -> bool {
        self.refresh.swap(refresh, Ordering::Relaxed)
    }
}
```
A store with no refresh-on-hit mode (like `TtlSortedCache`) implements neither new trait; drop the
old no-op methods entirely rather than porting them.

### 32. TTL stores track per-entry expiry; `set_ttl` affects future inserts only

`TtlCache`, `LruTtlCache`, `ShardedTtlCache`, and `ShardedLruTtlCache` now store the computed
expiry timestamp alongside each entry rather than recomputing it from the global TTL on every
lookup. `set_ttl` (and `unset_ttl`) changes the TTL used for future insertions; entries already
in the store keep their original expiry.

Previously, changing the global TTL retroactively affected all entries because the expiry was
computed at lookup time from the current TTL. That behavior is gone.

`refresh_on_hit` still works as before: on a hit it recomputes the entry's expiry from the
current TTL as of the access time.

Detection: `grep -rn 'set_ttl\|unset_ttl'` -- call sites that relied on `set_ttl` retroactively
changing when existing entries expire.

Action: to change the expiry of entries already in the store, re-insert them. Call sites that
only use `set_ttl` to configure the TTL before insertions are unaffected.

### 33. `Cached` trait: `type Error` associated type required; `cache_try_set` / `try_set` return `Result<Option<V>, Self::Error>`

`Cached` gained an associated `type Error`. Every `impl Cached` must declare it. The return type
of `cache_try_set` (and its `try_set` alias) changed from `Result<Option<V>, Box<dyn Error>>` to
`Result<Option<V>, Self::Error>`.

Built-in mappings: every in-memory store (including `TtlCache`, `LruTtlCache`, and
`TtlSortedCache`) sets `type Error = std::convert::Infallible`. A TTL that would overflow
`Instant` bounds stores the entry with no expiry (never expires) instead of erroring, so no
in-memory set path fails.

Detection:
- A custom `impl Cached` without `type Error` fails with `E0046`.
- A call site that bound the error to a concrete error type fails with a type mismatch.

Action:
```rust
// Custom impl -- add the associated type
impl Cached<K, V> for MyStore {
    type Error = std::convert::Infallible; // or your error type
    // ...
}

// Call site -- drop the concrete error annotation
let _: Result<Option<V>, std::convert::Infallible> = cache.try_set(k, v);
// or just let inference work:
let _ = cache.try_set(k, v);
```

### 34. Sharded stores expose inherent `get`/`set`/`remove`/`remove_entry`/`delete`/`reset` returning unwrapped values

The six concrete sharded types (`ShardedUnboundCache`, `ShardedLruCache`, `ShardedTtlCache`,
`ShardedLruTtlCache`, `ShardedExpiringCache`, `ShardedExpiringLruCache`) now have inherent
methods `get`, `set`, `remove`, `remove_entry`, `delete`, and `reset` that return unwrapped
values (`Option<V>`, `()`, `bool`) instead of `Result<Option<V>, Infallible>`.

These inherent methods take priority over the same-named `ConcurrentCached` trait aliases when
called through a concrete type, so `store.get(&k)` now returns `Option<V>` directly.

Detection: a type mismatch where code previously matched on `Result` from a sharded store's
`get`/`set`/`remove`/`delete`/`reset`.

Action:
```rust
// Before -- used Result because the trait alias returned Result<_, Infallible>
let v: Result<Option<V>, _> = store.get(&k);
// After -- inherent method returns Option<V> directly
let v: Option<V> = store.get(&k);
```

To use the `Result`-returning trait methods, call through the `ConcurrentCached` trait or use
the `cache_`-prefixed trait methods:
```rust
use cached::ConcurrentCached;
let v = ConcurrentCached::cache_get(&store, &k); // Result<Option<V>, Infallible>
let v = store.cache_get(&k);                     // also Result<Option<V>, Infallible>
```

### 37. `cached`'s `async` feature no longer pulls `tokio`; `async_sync` re-exports changed

The `async` feature previously implied `tokio` as a dependency. It now only pulls `async-lock`
(runtime-agnostic). The `blocking` crate moved to the `redb_store` feature (#56); smol/async-std
async users no longer compile tokio or blocking.

`cached::async_sync::{Mutex, RwLock, OnceCell}` now re-export from `async-lock` instead of
`tokio::sync`. The API surface is similar but not identical: `OnceCell` from `async-lock` has
no `const_new()` method.

Detection: direct use of `cached::async_sync::OnceCell::const_new()` fails.

Action: replace `const_new()` with `OnceCell::new()` (or construct lazily with
`OnceCell::get_or_init`). If you need tokio-specific sync primitives, depend on `tokio` directly.

### 38. `RedbCacheError::BackgroundTaskFailed` variant removed

The `RedbCacheError::BackgroundTaskFailed` variant is removed. The async `RedbCache` now runs
blocking redb work on the `blocking` crate's thread pool instead of tokio's `spawn_blocking`,
so there is no background-task failure path.

Detection: an exhaustive `match` on `RedbCacheError` with a `BackgroundTaskFailed` arm fails
with an unknown-variant error.

Action: remove the `BackgroundTaskFailed` arm. The `#[non_exhaustive]` annotation on
`RedbCacheError` requires a wildcard arm regardless.

### 39. `sync_writes = "by_key"` on `#[cached]` (unchanged from 2.x)

**Nothing to migrate.** Both the attribute and the default are unchanged from 2.0.2. This section
is a reference for the mode's semantics and hazards, not a change to act on.

The default for a bare `#[cached]` (no `sync_writes` attribute) is no synchronization. Concurrent
uncached calls for the same key may each compute independently and overwrite each other, matching
Python's `functools.lru_cache` behavior.

`sync_writes = "by_key"` is an explicit opt-in (available since 0.55.1). When set, bucketed per-key
locks deduplicate concurrent first calls for the same key, so the function body runs at most
once per key per miss window (false sharing between different keys that hash to the same bucket
is possible but rare with the default 64 buckets).

**Hazards of `"by_key"`**: the per-key bucket lock is held across the entire function body.
Do NOT use `sync_writes = "by_key"` on recursive or re-entrant memoized functions - if two
keys in the active call chain collide in the same bucket, the recursion will deadlock. Cache
hits under `"by_key"` also take the per-key lock, so concurrent readers of the same key
serialize.

`#[once]` and `#[concurrent_cached]` defaults are unchanged.

`result_fallback` with no explicit `sync_writes` uses `Disabled` (the default), since the
fallback logic requires its own coordination that is incompatible with per-key deduplication.
Using an explicit non-Disabled `sync_writes` together with `result_fallback` is a compile error.

To opt in to per-key deduplication:
```rust
// Default: no synchronization (unchanged from 2.x)
#[cached]
fn compute(x: u64) -> u64 { expensive(x) }

// Explicit opt-in: deduplicate concurrent first calls per key
#[cached(sync_writes = "by_key")]
fn compute_dedup(x: u64) -> u64 { expensive(x) }
```

### 40. Macro attributes `convert`, `create`, `force_refresh`, `map_error`, `cache_prefix_block` accept unquoted Rust

These attributes previously required the value to be a quoted string:
`convert = r#"{ format!("{a}") }"#`. They now also accept unquoted Rust directly:
`convert = { format!("{a}") }`. The quoted-string form still works.

`ty` and `key` remain quoted strings (they hold type names and key expressions that the macro
parses as tokens, not inline Rust blocks).

`force_refresh` still requires the block form; a bare literal like `force_refresh = true` is
rejected with an error pointing at the block form.

Detection: no compile error for existing quoted-string forms. This is purely additive.

Action: no change required. Optionally update to the shorter unquoted form:
```rust
// Before (still valid)
#[cached(convert = r#"{ format!("{a}") }"#, map_error = "|e| MyErr(e)")]
// After (also valid -- prefer for readability)
#[cached(convert = { format!("{a}") }, map_error = |e| MyErr(e))]
```

### 41. `map_error` optional on `#[concurrent_cached(disk = true)]` and Redis stores

When `map_error` is omitted from a `#[concurrent_cached]` annotation that uses a disk or Redis
store, the generated code uses `.map_err(Into::into)?`. The function's error type must implement
`From<RedbCacheError>` (disk) or `From<RedisCacheError>` (Redis) for this to compile.

Detection: no compile error if the function's error type already implements the required `From`.
If `From` is not implemented, the error is a type mismatch at `.map_err(Into::into)?`.

Action: either supply `map_error` as before, or implement `From<RedbCacheError>` /
`From<RedisCacheError>` for your error type and omit `map_error`:
```rust
// map_error still accepted (no change needed)
#[concurrent_cached(disk = true, map_error = |e| MyErr::Disk(e))]
fn compute(n: u64) -> Result<String, MyErr> { ... }

// New: omit map_error when From is implemented
impl From<cached::RedbCacheError> for MyErr { ... }

#[concurrent_cached(disk = true)]
fn compute(n: u64) -> Result<String, MyErr> { ... }
```

### 42. `companions_vis` macro attribute sets visibility of generated companion functions

`#[cached]`, `#[once]`, and `#[concurrent_cached]` now accept a `companions_vis` attribute to
control the visibility of their generated companions independently of the cached function's own
visibility. `#[cached]` controls both the callable `{fn}_no_cache` and `{fn}_prime_cache`;
`#[once]` and `#[concurrent_cached]` emit only `{fn}_prime_cache` as a free companion (their
uncached body is a nested inner function, not a callable `{fn}_no_cache`).

```rust
// Make companions pub(crate) even though the cached fn is pub
#[cached(companions_vis = "pub(crate)")]
pub fn compute(x: u64) -> u64 { x * 2 }

// Make companions private
#[cached(companions_vis = "")]
pub fn compute(x: u64) -> u64 { x * 2 }
```

The default is to inherit the cached function's visibility (unchanged behavior). This is
additive -- no action required.

### 43. `TtlSortedCacheError` removed; TTL set paths are infallible

`TtlSortedCacheError` is removed with no replacement error type. All three TTL stores
(`TtlCache`, `LruTtlCache`, `TtlSortedCache`) treat a TTL that would overflow `Instant`
bounds as never-expires instead of erroring, so their `Cached::Error` is
`std::convert::Infallible` and no set path fails. See #18 and #22.

Detection: `cannot find type TtlSortedCacheError` at an import or a type annotation.

Action: drop the error import and any error handling on set paths.
```rust
// Before
use cached::TtlSortedCacheError;
let _: Result<Option<V>, TtlSortedCacheError> = cache.try_set(k, v);
// After
let _ = cache.try_set(k, v); // Err is Infallible
```

Detection: `the package 'cached' does not contain this feature: disk_store`.

### 45. `redis_ahash` cargo feature removed

The `redis_ahash` feature (which enabled the `redis` crate's optional `ahash` feature) is removed.
It gated no `cached` code.

Detection: `the package 'cached' does not contain this feature: redis_ahash`.

Action: drop `redis_ahash` from your feature list. To use `ahash` with `redis`, enable it on your

### 46. Redis values are serialized with MessagePack instead of JSON

`RedisCache` / `AsyncRedisCache` now serialize cached values with MessagePack (`rmp-serde`),
storing binary values, matching the redb store. They previously used `serde_json` and stored
UTF-8 strings. The `redis_store` feature pulls both `rmp-serde` and `serde_json` (the latter is
retained for the backward-read fallback that transparently reads 2.x JSON entries; see Action
below).

Detection: any external reader (outside of `cached`) that interprets `RedisCache` key values as
JSON strings; new writes are MessagePack binary and will not parse as JSON.

Action: old (2.x) JSON-format entries are read transparently. On a get, the store tries
MessagePack first; if that fails and the raw bytes look like a JSON object with a `version` key
(the 2.x format), it falls back to `serde_json` deserialization and serves the value. No
recompute happens; there is no cache stampede. Old entries are rewritten as MessagePack on their
next write (natural TTL expiry or an explicit set). Redis is often a shared cache, so this
backward-read fallback means a rolling upgrade of your application does not invalidate existing
entries mid-deploy.

One additional caveat: `RedisCacheError`'s serialize/deserialize variants no longer carry a
concrete `serde_json::Error` source (the cause is now a boxed
`Box<dyn std::error::Error + Send + Sync>`, see #7 and #59).

### 47. `connection_string()` returns a `ConnectionString` newtype; redacts by default

`RedisCache::connection_string()` and `AsyncRedisCache::connection_string()` now return a
`ConnectionString` newtype instead of a plain `String`. Both `Display` and `Debug` on
`ConnectionString` redact credentials (passwords masked). Call `.reveal()` on the returned value
to get the raw URL string.

Detection: code that used the `String` return value directly (passed it to a function expecting
`String`, or compared it against a raw URL string) will fail to compile.

Action: call `.reveal()` when you need the raw URL (for example to open a second connection).
For logging, use the value directly (redacted `Display`/`Debug`).

`resolve_connection_string()` likewise now returns a `ConnectionString` instead of a raw
`String`, so the resolved (possibly env-sourced) URL is redacted by the same newtype. And the
blanket `#[from] redis::RedisError` on `RedisCacheBuildError::Connection` is removed, so a raw
`redis::RedisError` no longer `?`-converts into the build error; build-path connection errors are
now constructed from a sanitized error, closing a credential-leak vector.

Detection: `.resolve_connection_string()?` used where a `String` is expected fails to compile;
`?`-converting a raw `redis::RedisError` into `RedisCacheBuildError` no longer compiles.

Action: call `.reveal()` on the `ConnectionString` when you need the raw URL. Where you previously
relied on `?` to turn a `redis::RedisError` into the build error, construct the
`RedisCacheBuildError::Connection` explicitly (or map the error) so credentials are not carried
into the message.

### 48. Redis TTL uses millisecond precision

`RedisCache` / `AsyncRedisCache` now set expiry with the millisecond commands `PSETEX` / `PEXPIRE`
and convert the configured TTL to milliseconds. Previously sub-second TTLs were rounded up to the
next whole second via `SETEX` / `EXPIRE`.

Detection: a sub-second TTL (`ttl_millis = N` below 1000, or a `Duration` with a fractional
second) on a Redis-backed cache now expires at the requested millisecond instead of at the next
whole second.

Action: none unless you relied on the round-up. Whole-second TTLs are unchanged. Requires Redis
2.6 or newer (the millisecond commands; 2.6 shipped in 2012).

### 49. `cache_reset` no longer preserves preallocated capacity

`Cached::cache_reset` (and `ConcurrentCached::cache_reset` / `ConcurrentCachedAsync::async_cache_reset`)
no longer retains the originally configured capacity. `UnboundCache` calls `clear()` followed by
`shrink_to(initial_capacity)`; `LruCache::cache_reset` instead rebuilds a fresh table reserved to
the live entry count. Either way, the allocator may shrink the backing allocation, so a reset
cache may reallocate on subsequent inserts up to the originally configured capacity.

Detection: code that called `cache_reset` expecting the backing allocation to remain at the
originally configured size (and thus to avoid reallocation after reset) will see that the
behavior has changed.

Action: if retaining the preallocated capacity matters (for example to avoid allocation jitter
in a hot path), recreate the cache with the same builder settings instead of calling
`cache_reset`.

Setting `true` surfaces the failure as `Err(RedbCacheError::CacheDeserialization { .. })` / `Err(RedisCacheError::CacheDeserialization { .. })` and leaves the entry in place. Note that the self-heal default is a behavior change: an undecodable entry (from a format change or corruption) is silently dropped rather than erroring; opt into `strict_deserialization(true)` if you need corruption surfaced. Imported via the prelude. `#[concurrent_cached]` automatically prefers this borrowed setter for any store that implements the trait (built-in or a custom `ty`/`create` store), so a custom serialize-backed store no longer pays a value clone on each set.

Sub-second precision is honored by the in-memory, disk (redb), and Redis stores; Redis uses the millisecond commands `PSETEX` / `PEXPIRE` (see #48).

All three builder methods (`ttl`, `ttl_secs`, `ttl_millis`) target the same underlying field; whichever is called last wins.
- `force_refresh = "{ <bool expr> }"` macro attribute (`#[cached]` / `#[concurrent_cached]` / `#[once]`) - a curly-brace expression block over the function's arguments (like `convert`); when it evaluates true, bypass the cached value and recompute. For a dedicated flag argument on `#[cached]` / `#[concurrent_cached]` you must exclude it from the key via `key` / `convert` (otherwise the `flag = true` call recomputes into a different key slot than the `flag = false` calls read, so the refresh is never seen). On `#[once]` there is no per-call key, so the forced recompute simply overwrites the single shared value. This is now a *required* method (see breaking change #16); the built-in sharded and in-memory expiry stores implement it with a genuine side-effect-free read.
- `in_impl = true` macro attribute — cache a method inside an `impl` block (the cache static is emitted in the method body); a `self` receiver is allowed and excluded from the key. The `_prime_cache` companion is not generated for `in_impl` methods.
- `LruCache::set_max_size` / `try_set_max_size`, `LruTtlCache::set_max_size` / `try_set_max_size`, `ExpiringLruCache::set_max_size` / `try_set_max_size` — resize a live LRU-backed cache (evicts LRU entries when shrinking). All three `try_set_max_size` methods return `Result<Option<usize>, cached::SetMaxSizeError>` where the inner value is the previous bound (same shape as `set_max_size`; `ZeroMaxSize` on a zero argument). `SetMaxSizeError` is `#[non_exhaustive]`, so a match on it needs a wildcard arm.
- `ShardedLruCache::set_max_size` / `try_set_max_size`, `ShardedLruTtlCache::set_max_size` / `try_set_max_size`, `ShardedExpiringLruCache::set_max_size` / `try_set_max_size` — runtime capacity resize on the sharded LRU stores. Shrinking evicts LRU-excess entries per shard strictly by recency (TTL/expiry state is ignored; call `evict()` first to sweep expired entries preferentially), fires `on_evict`, and increments the eviction counter; the same ceiling-division-plus-16-per-shard-floor policy the builders use is applied. Resize is not atomic across shards (shards are locked and resized one at a time, so concurrent readers may briefly observe mixed per-shard capacities). Return type matches the non-sharded `set_max_size` / `try_set_max_size`. On the sharded stores only, `try_set_max_size` returns `SetMaxSizeError::CapacityOverflow` when `max_size` is near `usize::MAX` and cannot be represented as a per-shard capacity; the infallible `set_max_size` panics in that case.
- `per_shard_initial_capacity(n)` on `ShardedUnboundCacheBuilder`, `ShardedTtlCacheBuilder`, and `ShardedExpiringCacheBuilder` — per-shard preallocation hint, the sharded counterpart of the single-owner builders' `initial_capacity` (total preallocation is `shards * per_shard_initial_capacity`). The LRU-bounded sharded builders size their shards from `max_size` / `per_shard_max_size` and do not take a separate hint.
- `ExpiringLruCache::retain(keep)` — removes entries that are expired or fail the predicate, firing `on_evict` and counting evictions; matches `LruTtlCache::retain`. `LruCache::retain` (no expiry dimension) removes solely on the predicate.
- `RedisCache` / `AsyncRedisCache` now implement `cache_clear` / `async_cache_clear` (namespace-scoped `SCAN` + `DEL`); `cache_reset` / `async_cache_reset` delegate to them (redis tracks no in-memory metrics).
- Reference arguments (`&T`, `Option<&T>`) now form the default macro key without a `convert`.
- `Expires::expires_at(&self) -> Option<cached::time::Instant>` -- default trait method returning the value's expiry instant when tracked (`None` by default / when unknown). Advisory/observability only; `is_expired()` remains the authoritative liveness check. Existing `impl Expires` blocks (which provide only `is_expired`) get the default for free. The instant type is the crate's `time::Instant` (`web_time` on wasm, `std` elsewhere), not `std::time::Instant`; a custom override must use that type.
- Inherent `peek(&self, &K) -> Option<V>` on the six sharded stores -- a clone of the live value with no recency update, no TTL refresh, no hit/miss metrics, and no lazy removal of expired entries. The same contract is also reachable generically through the new `ConcurrentCachePeek` trait (`cache_peek` plus a defaulted `peek` alias, `Result<Option<V>, Self::Error>`, `Self::Error = Infallible` on the sharded stores); the inherent shim keeps call-site priority on the concrete types. `RedisCache` / `RedbCache` / `AsyncRedisCache` deliberately do not implement it. In `cached::prelude`.
- `Builder::new()` on the in-memory and sharded builders -- equivalent to the store's `::builder()`.
- `CachedExt::capacity` / `evictions` and `ConcurrentCachedExt::len` / `is_empty` / `hits` / `misses` / `capacity` / `evictions` -- ergonomic aliases for the corresponding `cache_*` accessors.
- `ConcurrentCached::cache_try_get_or_set_with` / `ConcurrentCachedAsync::async_cache_try_get_or_set_with` -- fallible-init get-or-set returning `Result<Result<V, E>, Self::Error>` (store error outer, closure error inner; nothing stored on a closure `Err`). Provided defaults. `ConcurrentCachedExt::try_get_or_set_with` is the short-alias form, delegating to `ConcurrentCached::cache_try_get_or_set_with`.
- `retain(keep)` on `UnboundCache`, `TtlCache`, `ExpiringCache`, `TtlSortedCache`, and all six sharded stores -- completes retain across every in-memory store. Every removed entry fires `on_evict`. On the expiry-aware stores, expired entries are removed regardless of the predicate and every removal counts an eviction; on `UnboundCache` / `ShardedUnboundCache` (no expiry dimension, no evictions counter) an entry survives exactly when `keep` returns `true`. The sharded form is `retain(&self, keep)`: it locks one shard at a time (not atomic across shards), the predicate runs under the shard write lock so it must not re-enter the cache, and `on_evict` fires after the shard lock is released, once per removed entry, in shard order. `retain` itself adds no `K: Clone` bound, so on the three `HashMap`-backed sharded stores (`ShardedUnboundCache`, `ShardedTtlCache`, `ShardedExpiringCache`) it is callable with a non-`Clone` key; the three LRU-backed stores require `K: Clone` for unrelated reasons (their enclosing impl block needs it for the LRU ring). `TtlSortedCache::retain` is distinct from the pre-existing `retain_latest(count, evict) -> usize`, which trims to the N latest-expiring entries by size rather than filtering by predicate. `retain` is inherent-only on both store families, not a trait method.
- `TtlSortedCache::capacity() -> Option<usize>` -- the configured size bound, `None` when unbounded.

- Custom hasher on the non-sharded in-memory stores: `UnboundCache`, `LruCache`, `TtlCache`, `LruTtlCache`, `TtlSortedCache`, `ExpiringCache`, and `ExpiringLruCache` gain a hasher type parameter defaulted to `DefaultHashBuilder` (`UnboundCache<K, V, S = DefaultHashBuilder>`, etc.) and a `.hasher(s)` builder method, mirroring the sharded stores. `DefaultHashBuilder` (ahash under the `ahash` feature, else std `RandomState`) is re-exported from the crate root. Existing code that names a store as `UnboundCache<K, V>` is unchanged; only explicit turbofish or stored-type annotations that need the third parameter are affected.
- Concurrent metrics through a trait: `ConcurrentCacheBase` gains `cache_hits` / `cache_misses` / `cache_capacity` / `cache_evictions` and a default `metrics() -> CacheMetrics`, so a `ConcurrentCached` / `ConcurrentCachedAsync` bound can read a sharded store's metrics generically (the inherent `metrics()` is retained). This mirrors the metric accessors already on `Cached`.
- `#[cached]` / `#[once]` now reject the concurrent-store-only attributes `disk`, `redis`, `map_error`, `shards`, `durable`, `disk_dir`, and `cache_prefix_block` with a clear error pointing to `#[concurrent_cached]`, instead of darling's generic "Unknown field" message. No change to which attributes are accepted.
- `len` / `cache_size` / `iter` / `evict` contract on lazy-eviction stores is now documented in one place: `len` / `cache_size` returns the stored count without scanning for expiry (so it may include expired entries), `iter` omits expired entries from the view without removing them, and `evict()` physically reclaims expired entries (and is how to obtain an accurate live count). Behavior is unchanged; see the `CachedIter` and `CacheEvict` docs.
- `ConcurrentCachedAsyncExt` — a blanket extension trait over `ConcurrentCachedAsync` with ten `async_`-prefixed aliases (`async_get`, `async_set`, `async_remove`, `async_remove_entry`, `async_delete`, `async_contains`, `async_clear`, `async_reset`, `async_get_or_set_with`, `async_try_get_or_set_with`), mirroring `ConcurrentCachedExt`. Re-exported from the crate root and `cached::prelude`. Gated on the `async_core` feature.
- `companions = false` macro attribute on `#[cached]`, `#[once]`, and `#[concurrent_cached]` — suppresses the generated `{fn}_no_cache` / `{fn}_prime_cache` companion functions. Combining it with `companions_vis` is a compile error.
- `#[concurrent_cached]` now accepts `result_fallback` together with `expires`.

## Additional breaking changes

All of the following are in 3.0.0 as well. They are listed separately only because they
landed after the entries above; coming from 2.x, apply them in the same pass.

### 50. `capacity()` renamed to `initial_capacity()` on allocation-hint builders

The `.capacity(n)` builder method on `UnboundCacheBuilder`, `TtlCacheBuilder`,
`TtlSortedCacheBuilder`, and `ExpiringCacheBuilder` is renamed to `.initial_capacity(n)`. The
method sets a pre-allocation hint on the backing `HashMap` without bounding entry count (that is
`max_size` on the LRU builders). The rename removes the ambiguity between a hint and an eviction
bound.

Detection: `no method named capacity found for struct UnboundCacheBuilder` (or the other three
builders).

Action: rename `.capacity(n)` to `.initial_capacity(n)`.
```rust
// Before
let cache = UnboundCache::<String, u32>::builder()
    .capacity(128)
    .build()?;

// After
let cache = UnboundCache::<String, u32>::builder()
    .initial_capacity(128)
    .build()?;
```
`max_size` on `LruCacheBuilder`, `LruTtlCacheBuilder`, and `ExpiringLruCacheBuilder` is
unchanged; it bounds entry count, not pre-allocation.

### 51. `Return<T>` fields are now private (`cached_proc_macro_types`)

`Return<T>::value` and `Return<T>::was_cached` are now private. They were public struct fields
accessible with `.value` / `.was_cached` or pattern syntax (`Return { value, was_cached }`).

Detection: `field value of struct Return is private` / `field was_cached of struct Return is
private`.

Action:
```rust
// Before
let r: Return<String> = my_fn();
println!("{}", r.value);
if r.was_cached { ... }

// After: use deref or into_inner() for the value, was_cached() for the flag
let r: Return<String> = my_fn();
println!("{}", *r);           // deref coerces to &T
// or
println!("{}", r.into_inner()); // consumes r, returns T
if r.was_cached() { ... }
```
Struct-pattern matches must also switch to the accessor methods (there is no destructure form
for private fields).

### 52. `set_max_size` returns `Option<usize>` on LRU stores

`LruCache::set_max_size`, `LruTtlCache::set_max_size`, and `ExpiringLruCache::set_max_size`
now return `Option<usize>` (the previous bound), matching `TtlSortedCache::set_max_size`.

Detection: a type mismatch where code expected `usize` from `set_max_size` on one of those three
types.

Action:
```rust
// Before
let prev: usize = cache.set_max_size(200);

// After
let prev: Option<usize> = cache.set_max_size(200);
// or just ignore it
cache.set_max_size(200);
```

### 53. ahash `runtime-rng` enabled on non-wasm targets

When the `ahash` feature is active, `cached` now enables `ahash/runtime-rng` on non-wasm
targets. The ahash hasher seeds itself from the OS RNG at startup instead of using a fixed
compile-time seed, closing a hash-flood denial-of-service vector.

This is transparent to source code. No API or type change.

On wasm32 targets `runtime-rng` is not enabled because it would require a `getrandom` wasm
backend. The compile-time seed is kept on wasm. If your wasm target uses `getrandom` already
(e.g. via `getrandom/js`), you can enable `ahash/runtime-rng` directly on your own `ahash`
dependency to opt in.

Detection: none -- no compile error and no source change required.

Action: none for non-wasm targets. wasm targets are unaffected.

### 54. Sharded `copy_from` returns `Result` instead of panicking

`copy_from(...)` on all six sharded builders (`ShardedUnboundCache`, `ShardedLruCache`,
`ShardedTtlCache`, `ShardedLruTtlCache`, `ShardedExpiringCache`, `ShardedExpiringLruCache`) now
returns `Result<_, BuildError>` and validates its configuration instead of panicking on an
invalid value.

Detection: an unused-`Result` warning at the `copy_from` call site, or a type mismatch binding the
result as the builder directly.

Action: handle the `Result`.
```rust
// Before
let b = builder.copy_from(&other);
// After
let b = builder.copy_from(&other)?;
```

### 55. redb cache names reject filename-invalid characters

`RedbCacheBuilder` now rejects a `cache_name` containing characters invalid in a filename: `:`
`<` `>` `"` `|` `?` `*`, path separators (`/` `\`), and ASCII control characters (including DEL).
An empty name and the path components `.` and `..` are also rejected. Previously a `:`-bearing
name (for example from `module_path!()`) was accepted but invalid on Windows/NTFS.

Detection: `RedbCacheBuildError::InvalidCacheName` at `build()` for a name that previously built.

Action: sanitize the name to the allowed set. A `module_path!()`-derived name needs its `::`
separators replaced (for example with `_`).

### 56. `blocking` moved from the `async` feature to `redb_store`

The `blocking` crate (and its `async-channel` / `futures-lite` transitive deps) is now pulled by
`redb_store` rather than `async`, since only the redb store uses it to offload synchronous disk
work off the async executor. Redis-only and in-memory async builds no longer pay for it.

Detection: a build that enabled `async` (without `redb_store`) and relied on `blocking` being
present transitively now fails to resolve `blocking`.

Action: depend on `blocking` directly if you used it transitively, or enable `redb_store`.

### 57. Redis capability features are additive and runtime-agnostic

Two changes to the redis feature axes:

- `redis_connection_manager` is now additive. Enabling it no longer swaps every `AsyncRedisCache`
  from a `MultiplexedConnection` to a `ConnectionManager`. The manager is a per-cache opt-in: call
  `.connection_manager(true)` on the builder for the caches that want auto-reconnect; every other
  cache keeps the multiplexed connection (the 2.x default). A transitive dependency enabling the
  feature can no longer change your cache's connection behavior.
- `redis_connection_manager` and `redis_async_cache` no longer pull a runtime (`redis_tokio`). The
  runtime is a separate axis: enable a runtime feature (`redis_tokio*` or `redis_smol*`) alongside
  the capability. A capability feature without a runtime fails to compile inside redis-rs.

Detection: a cache that silently used the connection manager (via the feature) now uses a
multiplexed connection unless you call `.connection_manager(true)`; a build that enabled only
`redis_connection_manager` or `redis_async_cache` now fails to compile for lack of a runtime.

Action: pair the capability with a runtime in `Cargo.toml`, and opt caches into the manager
explicitly.
```toml
# Before (2.x): the capability implied the tokio runtime and swapped every cache
cached = { version = "2", features = ["redis_connection_manager"] }
# After: pick a runtime explicitly; the manager is a builder opt-in
cached = { version = "3", features = ["redis_connection_manager", "redis_tokio"] }
```
```rust
// Opt a specific cache into the connection manager
let cache = AsyncRedisCache::builder("my_prefix")
    .connection_manager(true)
    .build()
    .await?;
```
Client-side caching is the same shape: `features = ["redis_async_cache", "redis_tokio"]` (or
`redis_smol`).

### 58. Trait-bound parity: `V: Clone` / `V: Eq`, and `#[concurrent_cached(ty = ...)]` requires `create`

Several trait bounds tightened for consistency:

- `CloneCached::cache_get_with_expiry_status` now carries `V: Clone`, matching its
  `cache_peek_with_expiry_status` sibling. A custom `impl CloneCached` for a `V` that is not
  `Clone` no longer compiles.
- `UnboundCache` / `LruCache` implement `Eq` only when `V: Eq` (previously the `Eq` impl did not
  require it).
- `#[concurrent_cached(redis = true, ty = ...)]` / `#[concurrent_cached(disk = true, ty = ...)]`
  without a `create = ...` is now a compile error (the macro cannot construct a `ty`-typed store
  without a constructor) instead of generating code that fails obscurely.

Detection: `the trait bound V: Clone`/`V: Eq is not satisfied` on the affected impls; a macro error
requiring `create` on a `ty`-typed concurrent cache.

Action: add the missing bound (`where V: Clone` / `V: Eq`) to your custom impl, or provide
`create = "..."` alongside `ty = "..."`.

Additive (no action required): `ConcurrentCachedExt` gained `clear` / `reset` aliases mirroring the
sync `CachedExt`.

### 59. redis/redb error sources are boxed (`Box<dyn Error + Send + Sync>`)

Every foreign cause on `RedisCacheError`, `RedisCacheBuildError`, `RedbCacheError`, and
`RedbCacheBuildError` is boxed as `source: Box<dyn std::error::Error + Send + Sync + 'static>`
(see #7). No `redis`, `r2d2`, or `redb` type appears in the public surface of these enums, so a
backend crate major bump is no longer a breaking change to them. `cached` does not re-export
`redis` or `redb`.

Detection: grep for `rmp_serde::`, `serde_json::`, `redis::RedisError`, or `redb::Error` used to
bind or match a `source` field; any such binding fails to compile.

Action:
- Match the variant, not the source type: `RedisCacheError` has `Redis { .. }` and
  `Pool { .. }`; `RedbCacheError`/`RedbCacheBuildError` have `Storage { .. }`; the
  serialize-backed enums (`RedbCacheError`, `RedisCacheError`) share
  `CacheSerialization { source }` and `CacheDeserialization { source, cached_value }`. No single
  enum has all five variants.
- To classify a decode failure without touching the source, use `is_deserialization()` on either
  error type.
- For logging, use `Display` / `Debug` on the error (the redacting `ConnectionString` still
  applies to connection errors, see #47).
- To inspect the concrete cause, downcast the boxed source. This requires a direct dependency on
  the backend crate at exactly the version `cached` uses (a version skew makes `downcast_ref`
  return `None` silently):
  ```rust
  if let RedisCacheError::Redis { source, .. } = &err {
      if let Some(redis_err) = source.downcast_ref::<redis::RedisError>() {
          // inspect redis_err
      }
  }
  ```
  Prefer variant matching and `is_deserialization()` where they suffice; downcasting is the
  version-coupled path.

### 60. `LruTtlCacheBuilder` gained a hasher type parameter in the third slot

`LruTtlCacheBuilder` went from `<K, V, E = NoEvict>` to
`<K, V, S = DefaultHashBuilder, E = NoEvict>`: the hasher is the third parameter and the
eviction typestate marker moved to fourth. Every builder in the crate now takes its hasher in
the third slot, `ShardedLruTtlCacheBuilder<K, V, H = DefaultShardHasher, E = NoEvict>`
included (that one is unchanged from 2.0.2).

This matters for positional annotations: `LruTtlCacheBuilder<K, V, HasEvict>` named the
eviction typestate in 2.0.2 and names the *hasher* in 3.0. It does not fail at the
annotation; it fails later, at `.build()`, with a note about `HasEvict` not implementing
`BuildHasher`.

Detection: grep for a spelled-out `LruTtlCacheBuilder<` type annotation naming three
parameters, or any annotation naming `NoEvict` / `HasEvict` positionally. Look for
`the trait bound `HasEvict: BuildHasher` is not satisfied` or a `build` method-not-found
error listing the two typestate impls.

Action: name the hasher third and the typestate fourth
(`LruTtlCacheBuilder<K, V, HasEvict>` -> `LruTtlCacheBuilder<K, V, DefaultHashBuilder, HasEvict>`,
or use the concrete hasher you passed to `.hasher(..)`). Type-inferred uses and the defaults
need no change.

### 61. `dep:`-gated internal dependencies are not public feature names

`rmp-serde`, `serde_json`, and `r2d2` are declared as `dep:rmp-serde` / `dep:serde_json` /
`dep:r2d2` inside the feature definitions. This makes them private to the feature resolver and
removes them as public feature names. Any `features = ["rmp-serde"]` in a `Cargo.toml` now
produces: `the package 'cached' does not contain this feature: rmp-serde`.

These deps are pulled in automatically by `redis_store` (rmp-serde, serde_json, r2d2) and
`redb_store` (rmp-serde). They are not selectable on their own.

`serde` is in the same category: it is **not** a public `cached` feature. In 2.0.2 it existed
only as the implicit feature of the optional `serde` dependency; no public item was gated on
it then and none is now (`SerializeCached` / `SerializeCachedAsync` are ungated and expose no
codec), so `features = ["serde"]` added a dependency and no API. The codec is an
implementation detail pulled directly by `redis_store` and `redb_store`.

Detection: `the package 'cached' does not contain this feature: X` for X in {serde,
rmp-serde, serde_json, r2d2}.

Action: remove the dep name from your `cached` features list. If you need the dep directly in
your own code, add it to your own `Cargo.toml` separately. The complete list of public `cached`
features is:

| Feature | Default | Description |
|---|---|---|
| `proc_macro` | yes | `#[cached]`, `#[once]`, `#[concurrent_cached]` macros |
| `ahash` | yes | ahash hasher for internal maps |
| `time_stores` | yes | `TtlCache`, `LruTtlCache`, `TtlSortedCache` |
| `async_core` | no | async trait definitions without a runtime |
| `async` | no | async support (`async-lock`; no tokio) |
| `redis_store` | no | synchronous Redis backend |
| `redis_tokio` | no | async Redis + tokio runtime |
| `redis_tokio_native_tls` | no | `redis_tokio` + native-tls |
| `redis_tokio_rustls` | no | `redis_tokio` + rustls |
| `redis_smol` | no | async Redis + smol runtime |
| `redis_smol_native_tls` | no | `redis_smol` + native-tls |
| `redis_smol_rustls` | no | `redis_smol` + rustls |
| `redis_connection_manager` | no | per-cache auto-reconnect opt-in |
| `redis_async_cache` | no | client-side caching (RESP3) |
| `redb_store` | no | disk-backed cache via redb |

### 62. `SerializeCached::cache_set_ref` / `async_cache_set_ref` return type changed to `Result<(), _>`

`cache_set_ref(&self, &K, &V) -> Result<Option<V>, Self::Error>` and its async counterpart
now return `Result<(), Self::Error>`. The previous-value round-trip on every write (a GET before
each SET on Redis) is eliminated.

Detection: a custom `impl SerializeCached` or `impl SerializeCachedAsync` that defines
`cache_set_ref` / `async_cache_set_ref` returning `Result<Option<V>, _>` fails with E0053
(incompatible return type).

Action: change the signature to return `Result<(), Self::Error>` and return `Ok(())`.
```rust
// Before
fn cache_set_ref(&self, k: &K, v: &V) -> Result<Option<V>, Self::Error> {
    // ... write to store ...
    Ok(Some(prev))
}
// After
fn cache_set_ref(&self, k: &K, v: &V) -> Result<(), Self::Error> {
    // ... write to store ...
    Ok(())
}
```
If you need the previous value, call `cache_get` before the set.

### 63. Concurrent introspection is `cache_size` / `cache_is_empty` (rc-era churn)

This only affects code written against an rc-era `ConcurrentCacheBase::len` /
`ConcurrentCacheBase::is_empty`. Coming straight from 2.x there is nothing to do: `ConcurrentCacheBase`
is new in 3.0, and the 2.0.2 concurrent traits carried neither name.

The introspection methods on `ConcurrentCacheBase` are `cache_size` and `cache_is_empty`. The
shorter `len` / `is_empty` names live on the `ConcurrentCachedExt` alias trait, returning
`Result<Option<usize>, Self::Error>` / `Result<Option<bool>, Self::Error>`.

The concrete sharded types retain their inherent `len(&self) -> usize` and `is_empty(&self) ->
bool` methods (which return plain values and take priority at the call site), so `store.len()` /
`store.is_empty()` on a concrete sharded type are unaffected.

Detection: fully-qualified `ConcurrentCacheBase::len(&store)` or `ConcurrentCacheBase::is_empty(&store)` calls.

Action:
```rust
// Before
let n = ConcurrentCacheBase::len(&store)?;
let empty = ConcurrentCacheBase::is_empty(&store)?;
// After
let n = store.cache_size()?;
let empty = store.cache_is_empty()?;
```

### 64. Redis and redb store builders take a required positional argument

`RedisCache::builder()`, `AsyncRedisCache::builder()`, and `RedbCache::builder()` now require
their primary identifier as a positional argument: `builder(prefix)` for the redis stores and
`builder(name)` for the redb store. The no-argument form no longer compiles.

This only affects code written against the rc-era no-argument `builder().name(...)` /
`builder().prefix(...)` form. Coming straight from 2.x, the net change is the one described in
#26: `builder(prefix, ttl)` becomes `builder(prefix)` with an optional `.ttl(...)` setter.

Detection: `RedisCache::builder()` / `AsyncRedisCache::builder()` / `RedbCache::builder()` with
no arguments now fails to compile. `RedisCacheBuilder::new()` / `RedbCacheBuilder::new()`
(the builder-struct constructors, not the cache-type methods) are unchanged.

Action:
```rust
// Before (the intermediate no-arg form some 3.0 release candidates shipped)
let b = RedbCache::<String, String>::builder().name("my-cache");
let b = RedisCache::<String, String>::builder().prefix("my_prefix");
let b = AsyncRedisCache::<String, String>::builder().prefix("my_prefix");
// After
let b = RedbCache::<String, String>::builder("my-cache");
let b = RedisCache::<String, String>::builder("my_prefix");
let b = AsyncRedisCache::<String, String>::builder("my_prefix");
```
`.ttl(...)` and other optional setters chain as before.

### 65. Redis TTL is now optional; no `MissingRequired("ttl")` from `build()`

`RedisCache::builder().build()` and `AsyncRedisCache::builder().build()` no longer return
`Err(RedisCacheBuildError::Build(BuildError::MissingRequired("ttl")))`. An unset TTL is valid
and means entries are written without an expiry command (a plain `SET`), so they never expire.

Detection: a `match` or `if let` that handled `RedisCacheBuildError::Build(BuildError::MissingRequired(f)) if f == "ttl"` to catch an absent TTL.

Action: remove that arm. If you want entries to expire, set `.ttl(Duration)` on the builder
explicitly. `Build(BuildError::InvalidValue)` remains reachable (zero TTL, empty prefix — see #9).

### 66. `#[concurrent_cached(disk = true, cache_prefix_block = ...)]` is now a compile error

Combining `disk = true` with `cache_prefix_block` on a `#[concurrent_cached]` annotation
previously silently ignored `cache_prefix_block`. The macro now rejects it with a compile error
stating that disk-backed caches identify their redb table by `name`, not by a key prefix.

Detection: a `#[concurrent_cached(disk = true, cache_prefix_block = ...)]` annotation that
previously compiled but whose `cache_prefix_block` had no effect.

Action: remove `cache_prefix_block` from the annotation. The redb table name is set via
`name = "..."`:
```rust
// Before (cache_prefix_block was silently ignored)
#[concurrent_cached(disk = true, cache_prefix_block = { format!("pfx") })]
fn compute(x: u64) -> Result<String, MyErr> { ... }
// After
#[concurrent_cached(disk = true, name = "compute")]
fn compute(x: u64) -> Result<String, MyErr> { ... }
```

### 67. `RedisCacheBuildError::Resp2DowngradeWithClientSideCaching` is gated behind `redis_async_cache`

The variant is only constructible when the `redis_async_cache` feature is enabled, and is now
only declared there. A `match` arm naming it in a build without `redis_async_cache` no longer
compiles. The enum is `#[non_exhaustive]`, so exhaustive matches already carry a `_` arm.

Detection: `error[E0599]: no variant named Resp2DowngradeWithClientSideCaching` in a build
without the `redis_async_cache` feature.

Action: gate the arm with `#[cfg(feature = "redis_async_cache")]` or drop it and rely on the
`_` arm.

### 68. `#[cached]` rejects `sync_writes_buckets` without `sync_writes = "by_key"`

Using `sync_writes_buckets = N` on `#[cached]` without `sync_writes = "by_key"` is now a compile
error. The attribute was previously accepted and silently ignored; buckets only exist on the
`by_key` path. `#[once]` already rejected this combination before this change.

Compile error text:
```
error: `sync_writes_buckets` only applies to `sync_writes = "by_key"` (it sets the number of
per-key lock buckets); it has no effect with any other `sync_writes` mode. Add
`sync_writes = "by_key"` or remove `sync_writes_buckets`.
```

Detection: grep for `sync_writes_buckets` and verify each site also has `sync_writes = "by_key"`.

Action: either add `sync_writes = "by_key"` to opt into per-key locking with the configured
bucket count, or remove `sync_writes_buckets` to keep the previous effective behavior (no write
synchronization):
```rust
// Before (compiled, sync_writes_buckets was silently ignored)
#[cached(sync_writes_buckets = 128)]
fn compute(x: u64) -> u64 { expensive(x) }

// After -- option A: opt into per-key locking with 128 buckets
#[cached(sync_writes = "by_key", sync_writes_buckets = 128)]
fn compute(x: u64) -> u64 { expensive(x) }

// After -- option B: remove the inert attribute (keeps no-synchronization default)
#[cached]
fn compute(x: u64) -> u64 { expensive(x) }
```

### 69. `disk_directory(...)` builder method renamed to `disk_dir(...)`

The disk-store builder's directory setter is renamed, matching the macro attribute
`disk_dir = "..."`. This is on top of the `DiskCacheBuilder` -> `RedbCacheBuilder` type rename
(#23): renaming the type alone still fails to compile if the old method name is used.

Detection: `grep -rn 'disk_directory('`

Action:
```rust
// Before
DiskCacheBuilder::new("cache_name").disk_directory("/var/cache/my-app")
// After
RedbCache::builder("cache_name").disk_dir("/var/cache/my-app")
```

### 70. Sharded TTL stores: inherent `ttl`/`set_ttl`/`unset_ttl`/`refresh_on_hit`/`set_refresh_on_hit` removed; use `ConcurrentCacheTtl`

The runtime TTL controls on the sharded TTL-capable stores (`ShardedTtlCache`,
`ShardedLruTtlCache`) are no longer inherent methods; they live only on traits (same names, same
signatures, still `&self`), split across two traits: `ttl`/`set_ttl`/`unset_ttl` on
`ConcurrentCacheTtl`, and `refresh_on_hit`/`set_refresh_on_hit` on the new
`ConcurrentCacheRefreshOnHit` (see #31). This makes the concurrent family uniform: `RedisCache`,
`AsyncRedisCache`, and `RedbCache` already exposed these controls only through traits, and
implement both `ConcurrentCacheTtl` and `ConcurrentCacheRefreshOnHit`. The single-owner
counterpart is #20 (`TtlCache` / `LruTtlCache` via `CacheTtl` / `CacheRefreshOnHit`). Builder
setters (`.ttl(...)`, `.refresh_on_hit(...)`) are unaffected.

Detection: `no method named set_ttl`/`ttl`/`unset_ttl` or `refresh_on_hit`/`set_refresh_on_hit`
found for struct `ShardedTtlCache`/`ShardedLruTtlCache` -- the compiler suggests the trait import.

Action:
```rust
// Before -- inherent methods, no import needed
cache.set_ttl(Duration::from_secs(30));
cache.set_refresh_on_hit(true);
// After -- same calls, traits must be in scope
use cached::{ConcurrentCacheTtl, ConcurrentCacheRefreshOnHit}; // or `use cached::prelude::*;`
cache.set_ttl(Duration::from_secs(30));
cache.set_refresh_on_hit(true);
```

### 71. `Cached::Error` and `ConcurrentCacheBase::Error` require `std::error::Error + Send + Sync + 'static`

Both associated `Error` types now carry the bound
`std::error::Error + Send + Sync + 'static`.

Detection: `the trait bound MyError: std::error::Error is not satisfied` or similar `Send`/`Sync`
errors when implementing `Cached` or `ConcurrentCacheBase` with a custom error type.

Action: implement `std::error::Error` for your error type (and ensure it is `Send + Sync + 'static`):
```rust
#[derive(Debug)]
struct MyStoreError(String);

impl std::fmt::Display for MyStoreError {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        write!(f, "store error: {}", self.0)
    }
}

impl std::error::Error for MyStoreError {}
```
Using `thiserror::Error` derive satisfies the bound automatically.
All built-in error types (`std::convert::Infallible`, `RedisCacheError`,
`RedbCacheError`) already satisfy the bound and require no changes.

### 72. `ConcurrentCached::cache_contains` and `async_cache_contains` are now required; `V: Clone` bound removed

`cache_contains` on `ConcurrentCached` and `async_cache_contains` on `ConcurrentCachedAsync` are
now required methods. The previous defaulted versions (shipped only in 3.0.0 rcs) carried a
`V: Clone` (async: `V: Clone + Send`) bound; the required methods drop that bound entirely.
`ConcurrentCachedExt::contains` also drops its `V: Clone` bound.

Built-in stores: the six sharded stores keep their peek-based implementations (read lock, no
clone, no metrics); `RedisCache`, `AsyncRedisCache`, and `RedbCache` gain explicit get-based
implementations.

Detection: grep your code for `impl ConcurrentCached` and `impl ConcurrentCachedAsync` on your
own store types. Any such impl now fails with `E0046` ("not all trait items implemented, missing:
`cache_contains`") if the method is absent.

Action: add both methods to each impl. A get-based body is the simplest correct implementation:

```rust
impl ConcurrentCached<String, u32> for MyStore {
    // ...existing methods...
    fn cache_contains(&self, k: &String) -> Result<bool, Self::Error> {
        self.cache_get(k).map(|v| v.is_some())
    }
}

impl ConcurrentCachedAsync<String, u32> for MyStore {
    // ...existing methods...
    async fn async_cache_contains(&self, k: &String) -> Result<bool, Self::Error> {
        self.async_cache_get(k).await.map(|v| v.is_some())
    }
}
```

### 73. `TtlSortedCache::set_ttl` inherent method removed; use `CacheTtl`

The inherent `set_ttl` method on `TtlSortedCache` is removed. Runtime TTL controls are now only
on the traits: `CacheTtl` for single-owner stores, `ConcurrentCacheTtl` for concurrent stores.
This matches the pattern established for `TtlCache` / `LruTtlCache` (see #20) and for the
sharded TTL stores (see #70).

Detection: grep for `\.set_ttl(` on a `TtlSortedCache` value where `use cached::CacheTtl` (or
`use cached::prelude::*`) is not already in scope. A `no method named set_ttl found for struct
TtlSortedCache` error surfaces at the call site.

Action: import the trait. The call is otherwise unchanged:

```rust
use cached::CacheTtl; // or `use cached::prelude::*;`
// Before (inherent, no import needed)
cache.set_ttl(Duration::from_secs(30));
// After (same call, trait must be in scope)
cache.set_ttl(Duration::from_secs(30));
```

Note: `unset_ttl` and `ttl` were already trait-only on `TtlSortedCache`; only `set_ttl` had an
inherent duplicate that is now removed. `refresh_on_hit` and `set_refresh_on_hit` are a separate
story: in 2.0.2 they were trait-only via `CacheTtl` but no-ops (the setter discarded its argument
and always returned `false`, since `TtlSortedCache`'s deadline-ordered index cannot support
refreshing an entry's expiry on read). In 3.0 `CacheTtl` no longer declares those two methods at
all (see #31), and `TtlSortedCache` implements neither replacement trait (`CacheRefreshOnHit`), so
it has no `refresh_on_hit`/`set_refresh_on_hit` in any form. Code that called them on a
`TtlSortedCache` was getting a silent no-op and now gets `no method named refresh_on_hit found`.

### 74. `iter_order` / `value_order` return `CacheValue`-wrapped values

`LruCache`, `LruTtlCache`, and `ExpiringLruCache` share one shape for the recency-order
accessors: `iter_order() -> Vec<(K, CacheValue<V, M>)>` and
`value_order() -> Vec<CacheValue<V, M>>` (`key_order() -> Vec<K>` is unchanged).
`CacheValue<V, M>` (re-exported from the root) derefs to `V`, compares directly against bare
values (`PartialEq<V>`), and exposes `value()` / `into_value()`. `M` is per-entry metadata:
`()` for `LruCache` / `ExpiringLruCache`, `Option<Instant>` for `LruTtlCache`, where
`expires_at()` returns the entry's expiry (`None` means never expires). The 2.x
`LruTtlCache` shapes exposing bare `(Option<Instant>, V)` tuples are gone.

Detection: type mismatches at `iter_order` / `value_order` call sites, e.g.
`expected Vec<(K, V)>, found Vec<(K, CacheValue<V>)>`.

Action: destructure through the wrapper.
```rust
// Read through Deref, or unwrap explicitly:
for (k, v) in cache.iter_order() {
    println!("{k}: {}", *v);
}
let vals: Vec<V> = cache.value_order().into_iter().map(|v| v.into_value()).collect();
// LruTtlCache: expiry moves from the tuple to the accessor
let exp = cache.iter_order()[0].1.expires_at();
```

### 75. `TtlSortedCache` `insert*` replaced by `set` / `set_with` and made infallible

`insert` / `insert_ttl` / `insert_evict` / `insert_ttl_evict` are replaced by plain `set(k, v)`
and the `set_with(k, v)` entry-setter builder (`.ttl(Duration)` for a per-entry TTL override,
`.evict()` to opt into the post-insertion eviction sweep, terminal `.set() -> Option<V>`). Every
path now returns `Option<V>` (the displaced unexpired value) instead of `Result<Option<V>, _>`;
see #18 for the error removal.

Detection: grep for `insert_ttl_evict|insert_evict|insert_ttl|\.insert\(` on `TtlSortedCache`
call sites, or `no method named insert found for struct TtlSortedCache` (the compiler suggests
`set`).

Action: rename the call and drop the error handling.
```rust
// Before
cache.insert(k, v).unwrap();
cache.insert_ttl(k, v, Duration::from_secs(5)).unwrap();
cache.insert_evict(k, v, true).unwrap();
cache.insert_ttl_evict(k, v, Some(Duration::from_secs(5)), true).unwrap();
cache.insert_ttl_evict(k, v, None, true).unwrap();
// After
cache.set(k, v);
cache.set_with(k, v).ttl(Duration::from_secs(5)).set();
cache.set_with(k, v).evict().set();
cache.set_with(k, v).ttl(Duration::from_secs(5)).evict().set();
cache.set_with(k, v).evict().set();
```

### Single-owner `contains` semantic change (rc surface only; no code change required)

`CachedExt::contains` now delegates to `Cached::cache_contains` (a new defaulted method on
`Cached`; built-in stores override it with a peek-based implementation) instead of delegating to
`cache_get`. As a result, `contains` on the built-in single-owner stores no longer counts a
hit/miss, promotes LRU recency, or refreshes the TTL on refresh-on-hit stores. Expired entries
are now reported as absent (`false`) rather than triggering eviction and returning a miss.

No code change is required. The trait-level default of `Cached::cache_contains` remains
get-based, so a custom `impl Cached` that does not override `cache_contains` keeps the previous
side-effecting behavior.

### 76. `cache_set` over an existing key promotes it to most-recently-used

`cache_set` over an existing key now promotes that key to most-recently-used. Previously the
value was replaced in place and the entry kept its position in the eviction order. This affects
`LruCache`, `LruTtlCache`, `ExpiringLruCache`, `ShardedLruCache`, `ShardedLruTtlCache`, and
`ShardedExpiringLruCache`, and it changes which entry a capacity eviction selects in
overwrite-heavy workloads: the overwritten key survives longer and another key becomes the
victim. It also changes `iter_order` / `value_order` after an overwrite, and the `on_evict`
victim sequence. It resolves a divergence on `ShardedLruTtlCache` / `ShardedExpiringLruCache`,
where configuring an `on_evict` callback changed eviction order because the callback branch
promoted an overwritten entry and the no-callback branch did not; both branches now promote.

Detection: code that overwrites existing keys with `cache_set` and relies on capacity eviction
selecting the least-recently-inserted entry, or that asserts on `iter_order` / `value_order`
after an overwrite.

Action: none required for correctness. There is no public API that writes a value without
touching recency; `cache_peek`, `cache_peek_with_expiry_status`, and `cache_contains` remain
non-promoting reads.

### 77. Default shard count of the LRU-bounded sharded stores is capped by `max_size`

The DEFAULT shard count of `ShardedLruCache`, `ShardedLruTtlCache`, and `ShardedExpiringLruCache`
(no explicit `.shards(n)` on the builder, and a total `max_size` rather than `per_shard_max_size`)
is now `next_power_of_two(max_size / 16).clamp(1, default_shard_count())` instead of the raw
`default_shard_count()` (`available_parallelism() * 4`, clamped to `[8, 1024]`). Small caches on
high-core-count hosts get fewer, larger shards: `ShardedLruCache::new(100)` resolves to 8 shards
with an effective `capacity()` of 128, where a 64-core box previously built 256 shards with a
capacity of 4096. `shards()`, `shard_sizes()`, and `capacity()` change accordingly, and per-shard
LRU eviction is coarser-grained since each shard holds a larger fraction of the entries.

An explicit `.shards(n)` is authoritative and unaffected. The `per_shard_max_size` path and the
unbounded stores (`ShardedUnboundCache`, and `ShardedTtlCache` / `ShardedExpiringCache` without a
`max_size`) keep `default_shard_count()`.

Detection: a test or invariant that asserts on `shards()`, `shard_sizes()`, or `capacity()` of a
default-constructed LRU-bounded sharded cache with a small `max_size`.

Action: pin the count with `.shards(n)` if you depend on a specific shard count. Otherwise none;
reads and writes are unchanged.

### 78. `ConcurrentCached::cache_contains` is dyn-callable (`where Self: Sized` dropped)

`cache_contains` no longer carries a `where Self: Sized` bound, so it is part of the vtable and
callable through `dyn ConcurrentCached<K, V, Error = E>`. This only affects out-of-crate
`ConcurrentCached` implementations written against a 3.0.0 rc that copied the `where Self: Sized`
clause onto their `cache_contains`: the override no longer matches the trait signature.

Detection: `E0053` (method `cache_contains` has an incompatible type / where-clause) on a custom
`impl ConcurrentCached` that repeated `where Self: Sized`.

Action: drop the `where Self: Sized` clause from your `cache_contains` implementation.
```rust
// Before
fn cache_contains(&self, k: &K) -> Result<bool, Self::Error>
where
    Self: Sized,
{ /* ... */ }
// After
fn cache_contains(&self, k: &K) -> Result<bool, Self::Error> { /* ... */ }
```

### 79. `evictions` counter increments before `on_evict` fires

Every in-memory store now increments the `evictions` counter before invoking `on_evict` for a
removed entry, on every removal path (evict/retain sweeps, `cache_remove` / `cache_remove_entry`,
lazy expiry removal in `cache_get`, `cache_set` over an expired entry, capacity eviction, the
`get_or_set` families). Previously `LruCache`, `TtlCache`, `LruTtlCache`, `ExpiringCache`, and
`ExpiringLruCache` counted after the callback returned on most paths, so a panicking callback
left the removal uncounted.

Detection: not grep-detectable. Observable only if an `on_evict` callback panics (the eviction
is now counted) or, on the sharded stores, if a callback reads `metrics().evictions`
concurrently (the count now includes the eviction the callback is observing).

Action: none required. Tests that assert an eviction count under a panicking `on_evict` must
expect the removed entry to be counted.

### 80. `retain` returns `usize` instead of `()`

`retain` on all thirteen stores that have it (`UnboundCache`, `LruCache`, `TtlCache`,
`LruTtlCache`, `TtlSortedCache`, `ExpiringCache`, `ExpiringLruCache`, and the six sharded stores)
now returns the number of entries removed by the call instead of `()`. The count includes entries
the predicate rejected plus, on the expiry-aware stores (`TtlCache`, `LruTtlCache`,
`TtlSortedCache`, `ExpiringCache`, `ExpiringLruCache`, and the sharded TTL/expiring variants),
entries removed because they had expired regardless of what the predicate returned; the two
categories are not distinguished in the return value.

There is no `#[must_use]` on `retain`, so a bare `cache.retain(...);` statement (the overwhelming
majority of call sites) still compiles unchanged -- the trailing semicolon discards the count
either way. The break is narrow: it only hits code that bound the result as `()`, e.g.
`let () = cache.retain(..);`, or a function/closure whose body ends in `cache.retain(..)` as its
tail expression while declaring a `()` return type.

Detection: not grep-detectable in general (`retain(` call sites that already end in `;` are
unaffected). Look for `let () = ` bound to a `retain` call, or a function/closure ending in
`.retain(..)` (no trailing semicolon) whose signature declares `-> ()` or has no `-> ` at all with
the call as its final expression: the compiler reports `expected (), found usize`.

Action: add a trailing semicolon (`cache.retain(|k, v| ...);`) to discard the count, or bind it
(`let removed: usize = cache.retain(...);`) if you want it. See
specs/design/0041-retain-returns-removed-count.md.

### 81. MSRV raised from 1.89 to 1.92

Detection: `cargo build` fails with an error like "package `cached vX.Y.Z` cannot be built because
it requires rustc 1.92 or newer, while the currently active rustc version is Z".

Action: update your toolchain to 1.92 or newer. The floor moved because the `async_core` feature

you enable.

### 82. New trait `ConcurrentCachePeekAsync<K, V>` (async mirror of `ConcurrentCachePeek`)

Additive. `ConcurrentCachePeekAsync<K, V>: ConcurrentCacheBase` provides a required
`async_cache_peek(&self, &K) -> Result<Option<V>, Self::Error>` (deliberately no default body)
plus a defaulted `async_peek` alias. Implemented by the six sharded stores
(`Self::Error = Infallible`), each delegating to its existing sync `cache_peek`. Re-exported from
`cached::prelude`.

`RedisCache`, `RedbCache`, and `AsyncRedisCache` implement NEITHER peek trait
(`ConcurrentCachePeek` nor `ConcurrentCachePeekAsync`), and this is deliberate: peek is an
in-memory concept -- for an IO-backed store there is no client-side recency chain to skip and no
client-side TTL state to leave alone, so every negative guarantee a peek promises is either
vacuous or unobservable, while the operation is still a full round trip. See
specs/design/0040-peek-is-an-in-memory-concept.md. Generic code bounded on either peek trait
therefore accepts only the six sharded stores.

Detection: this is purely additive, so there is nothing to detect from a break. It is relevant if
you wrote your own `ConcurrentCachedAsync` impl and expected a peek method on it (there is none;
peek is its own trait), or if you previously called `async_cache_peek` on a sharded store and got
`E0599` with rustc wrongly suggesting you append `.await` (that suggestion pointed at the
non-future sync `cache_peek`, which cannot be awaited); the new trait resolves that call.

Action: none required. To use it, bring `ConcurrentCachePeekAsync` (or `cached::prelude::*`) into
scope.

### 83. `TtlSortedSetBuilder` gains `.ttl_secs(n)` / `.ttl_millis(n)`

Additive. The `set_with(k, v)` entry-setter builder on `TtlSortedCache` (see #75) now has

Detection: none -- no compile error, purely new methods.

Action: none required. Optionally replace `.ttl(Duration::from_secs(n))` with `.ttl_secs(n)` for

### 84. `CacheValue` gains `Display` and a bulk-unwrap helper

Additive. `CacheValue<V, M>` (the wrapper `iter_order()` / `value_order()` return on `LruCache`,

Detection: none -- both are new items.

### 88. `#[cached]` / `#[once]` on a non-`Clone` return type emit one error instead of 3

### 89. `TtlSortedCache` reuses the stored key when overwriting an existing entry

`TtlSortedCache::cache_set` (and the other set paths) now reuse the stored key when overwriting an

Observable only for key types whose `Eq` ignores part of the payload (e.g. case-insensitive keys,

### 90. `ExpiringLruCache::cache_set` fires `on_evict` with the stored key rather than the caller's key

### 91. Any thread-safe `std::hash::BuildHasher` now implements `ShardHasher`; `DefaultShardHasher` no longer has its own `ShardHasher` impl

`ShardHasher<K>` (the sharded builders' `.hasher(h)` bound) and `std::hash::BuildHasher` (the
single-owner builders' `.hasher(h)` bound, and `HashMap::with_hasher`) used to be unrelated
traits, so a hasher accepted by `LruCacheBuilder::hasher` was rejected by
`ShardedLruCacheBuilder::hasher` with `E0277`. A blanket impl closes the gap:

```rust
impl<K, S> ShardHasher<K> for S
where
    K: std::hash::Hash,
    S: std::hash::BuildHasher + Clone + Send + Sync + 'static,
{
    fn shard_hash(&self, key: &K) -> u64 { self.hash_one(key) }
}
```

`std::hash::RandomState` and `ahash::RandomState` both now satisfy `ShardHasher<K>` directly, and
`DefaultShardHasher` (the sharded stores' default hasher type) takes the blanket path itself: it
now implements `BuildHasher` and reaches `ShardHasher` only through the blanket impl above, rather
than through its own hand-written `impl<K: Hash> ShardHasher<K> for DefaultShardHasher`, which is
removed (a type cannot implement both without a duplicate-impl error). `DefaultShardHasher` is
therefore now also usable with `HashMap::with_hasher` and `LruCacheBuilder::hasher`.

Consequence: **a type that implements `std::hash::BuildHasher` can no longer also carry a
hand-written `ShardHasher` impl** (that combination is now a coherence error, `E0119`). Custom
shard-routing hashers (numeric range, string prefix, tenant id) must be implemented on a type that
does not implement `BuildHasher`.

The shard-selection contract is unchanged: `(hash >> 32) & shard_mask` selects the shard, so a
`BuildHasher` whose `finish()` leaves the upper 32 bits constant still routes every key to shard
0. `std::hash::RandomState` (SipHash) and `ahash::RandomState` both diffuse entropy across all 64
bits and satisfy the contract.

Detection: an `E0119` "conflicting implementations of trait `ShardHasher<K>`" on a type that
implements both `std::hash::BuildHasher` and a hand-written `ShardHasher<K>`.

Action: keep exactly one of the two impls. If the type is a general-purpose hash builder, drop the
hand-written `ShardHasher` impl and rely on the blanket one. If the type performs custom
shard-routing logic that is not a real hash function, do not implement `BuildHasher` on it.

### 92. Redis keys use a fixed-arity, percent-escaped layout; distinct `(namespace, prefix, key)` triples always map to distinct redis keys

`generate_redis_key` used to join `namespace:prefix:key` without escaping interior colons, and
dropped an empty field along with its separator. Two consequences:

- `namespace="a:b", prefix=""` and `namespace="a", prefix="b"` both produced the key `a:b:k`, so
  two logically distinct caches silently overwrote each other's entries and `cache_clear` on
  either one deleted both (a test asserted this collision).
- A cache with an empty namespace and prefix `p` had the clear scope `p:*`, which covered every
  key of a cache whose namespace was `p`, whatever that cache's own prefix was. Clearing the first
  deleted all of the second's entries.

3.0 writes `{namespace}:{prefix}:{key}` with fixed arity and percent-escaped fields: every field
contributes a field and a separator (so a key always carries exactly two separators), and `:`
becomes `%3A` and `%` becomes `%25` inside a field. Distinct triples therefore always map to
distinct keys, and the two overlaps above are structurally impossible. A field containing neither
character is left byte-identical, so a key with a non-empty namespace and no `:`/`%` is unchanged.

Layout examples:

```
("cached-redis-store:", "my_prefix", "my_key") -> "cached-redis-store:my_prefix:my_key"  (unchanged)
("",                    "my_prefix", "my_key") -> ":my_prefix:my_key"                    (was "my_prefix:my_key")
("a:b",                 "p",         "k")      -> "a%3Ab:p:k"                            (was "a:b:p:k")
("ns",                  "",          "k")      -> "ns::k"                                (was "ns:k")
```

`RedisCacheBuilder::build()` rejects an empty prefix (see #9), so the empty-prefix row only
matters for the internal key-generation helper. Trailing colons on the namespace are still
trimmed, so `namespace("ns")` and `namespace("ns:")` remain the same namespace.

**This changes the on-wire redis KEY layout for any cache with an empty namespace, or with a `:`
or `%` in its namespace, prefix, or keys.** The value envelope's `version` field lives inside the
value, so it cannot describe a key layout change: after upgrading, an old key is not found under
its new form. The entry is simply recomputed and rewritten at the new key on the next access; the
old entry is left in place to expire on its original TTL (or needs manual cleanup if the cache has
no TTL).

Detection: not grep-detectable in application code. Observable as a one-time full miss (and
therefore a recompute) immediately after upgrading a redis cache in place: on every entry when the
cache sets `.namespace("")`, and otherwise on every entry whose namespace, prefix, or key contains
`:` or `%`. A cache that keeps a non-empty namespace and never uses those two characters is
unaffected.

Action: none required for the API surface; this is a wire-format change, not a code change. If a
shared redis instance cannot tolerate a one-time cache-miss wave for the affected keys, warm the
cache after upgrading, or avoid an empty namespace and `:`/`%` in namespace/prefix/key values.

### 93. `ShardedTtlCache::cache_set` / `ShardedExpiringCache::cache_set` overwrite semantics

An overwrite now always rebinds the stored key to the caller's key via a single `remove_entry` +
`insert` shape, whether or not `on_evict` is configured. In 2.x the no-callback path kept the
first-inserted key (the callback path already rebound). `on_evict` for a displaced expired entry
receives the displaced entry's own stored (key, value) pair, not the caller's key instance.

Observable only for key types whose `Hash`/`Eq` cover part of their fields (equal-but-distinguishable
instances); no code change needed otherwise.

Detection: code relying on `cache_remove_entry`/iteration returning the first-inserted key instance
from these two stores, or an `on_evict` callback relying on receiving the caller's key.

Action: none for keys whose equality covers all fields.
